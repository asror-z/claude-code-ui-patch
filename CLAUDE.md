# Smarts Claude Manager — Project Requirements

VS Code extension (`asrorz.smarts-claude-manager`) that patches the **Claude Code extension's own
bundled files** (`extension.js`, `webview/index.js`, `webview/index.css`) on disk to add UI knobs (font
sizes, diff-card options, plan-preview sizing) and a pack of always-on chat-webview behavior features
(search, export, date/time stamps, copy buttons, auto-continue on stream drop, etc.) that don't exist
natively in Claude Code.

## Build / Package / Test Commands

```bash
npm run compile          # tsc -p ./  (src/*.ts -> out/*.js)
npm run watch            # tsc -watch -p ./
npm test                 # node --test "tests/**/*.test.mjs"  (real-DOM regression tests, jsdom)
```

There is no lint script configured in `package.json`. Verification is:
- Compile (`npm run compile`) and check for TypeScript errors.
- `npm test` — real-DOM regression tests under `tests/*.test.mjs` (jsdom, `node --test`). Each test
  extracts the ACTUAL injected script string straight out of its `behaviorFeatures.*.ts` source (never a
  hand-copied re-implementation), evaluates it in a real jsdom `window` (`runScripts: "dangerously"` is
  required so `document`/`window` resolve as bare globals inside `window.eval()` — jsdom's default eval
  sandbox does not expose them, unlike a real browser/webview), builds a synthetic fixture DOM, drives the
  real `init()`/`run()`/`attach()` flow and a real button click, and asserts the real clipboard/DOM output.
  Add one `tests/<feature>.test.mjs` per `behaviorFeatures.*.ts` file whose DOM-extraction logic is prone
  to a "matches by class substring, assumes a single-container shape" class of bug (see the CopyButtons
  `contentRoots()` incident below) — this is the concrete form of [Always Test for Real](#files)'s "capture
  the real DOM and run the feature's own JS against it (jsdom), assert it tagged real elements" rule,
  applied to this project's own injected-script features.
- Run via **F5** (`.vscode/launch.json` "Run Extension" — opens an Extension Development Host window
  with this extension loaded; this project's default dev workflow).
- Ad-hoc scratch test scripts against a **disposable copy** of a real installed
  `anthropic.claude-code-*-win32-x64` extension folder (never the user's live `~/.vscode/extensions/`
  install) — the disk-mutating-apply/restore test pattern owned by `smarts-app-vscode` →
  `module/host-lifecycle.md`.
- Packaging: `vsce package` — see [Every `.vsix` Build Goes Into `build/`](#every-vsix-build-goes-into-build--owned-by-smarts-app-vscode) below.

## Architecture

### The patch target vs. this extension's own code

This extension's own code (`src/*.ts` → `out/*.js`, loaded as `main` by VS Code) is **not** what gets
patched. What gets patched is a **different, already-installed extension**: Anthropic's Claude Code
(`anthropic.claude-code-<version>-<platform>`), found by scanning the VS Code-family host's real
extensions directory for the newest matching folder (see `extensionsDirs()` below). Three files inside
that folder are the actual patch targets:

| File | What it controls |
|---|---|
| `extension.js` | Plan Mode preview webview (font sizes, CSP) |
| `webview/index.css` | Chat code-block font size, chat message-input-box (composer) font size, and related CSS |
| `webview/index.js` | Chat Edit/MultiEdit diff cards (a Monaco diff editor with hardcoded options), plus the injected chat-enhancement `<script>`/`<style>` block |

### `patcher.ts` — the patch engine (~2,600 lines, the core of this extension)

Everything about *how* a byte-level edit is made to Claude Code's files lives here. Three kinds of edits,
each with its own declarative table and apply/restore/analyze functions:

- **`PATCH_POINTS`** (`PatchPoint[]`) — a *size* swap: replaces a hardcoded px number or CSS value via an
  anchor regex. `pointSet()` / `pointRestore()` / `pointCurrentPx()`.
- **`TOGGLE_POINTS`** (`TogglePoint[]`) — a *boolean* flip (e.g. diff-card line numbers, the CSP patch,
  the always-on chat-enhancements injection gate). `toggleSet()` / `toggleCurrentOn()`.
- **`INJECT_POINTS`** (`InjectPoint[]`) — adds CSS/JS that doesn't exist natively (custom font family,
  the whole chat-enhancement feature bundle). `readInject()` / `injectEq()`.

Each point declares a `section: Section` (`"Chat Panel" | "Plan Preview"`) used to group rows in the
settings panel. `ALWAYS_ON_TOGGLES` (`chatEnhancements`, `faroCsp`) are toggles the UI can never turn off.

Top-level flow, in the order a caller actually invokes it:

1. **`findLatestClaudeExt(context)`** — resolves the real Claude Code install folder via
   `extensionsDirs(context)`, which reads `context.extensionUri` first (this is what makes discovery
   host-agnostic across every VS Code-family fork — see the "Must Work in EVERY VS Code-Based IDE"
   section below).
2. **`analyze()` / `analyzeToggles()` / `analyzeInjects()`** — read the three target files off disk and
   report each point's live status (`current` / `stock` / `custom` / `missing`) against the user's
   `smartsClaudeManager.*` settings — this drives the panel's green/yellow sync dots. Always a live read,
   never a cached assumption.
3. **`applyPatch()`** — the actual write. Loops over the three files; each file's edits are wrapped in
   their own try/catch (one file's write failure never aborts the others — see the EPERM/partial-apply
   incident further down), and every write goes through **`writeFileAtomic()`** (temp file + rename, with
   retry on `EPERM`/`EBUSY`/`EACCES` for Windows' transient post-update file locks).
4. **`restorePatch()`** — reverts every patched file back to its captured native/stock values
   (`captureStockValues()` records the pristine bytes the first time a file is touched, keyed by Claude
   Code version).
5. **`class Patcher`** (constructor + `register()`) — the stateful orchestrator: activation-time
   drift-check + `applyOnActivation()` (auto-applies and, if real edits were written, auto-reloads the
   window once), `discard()` / `enable()` / `restore()` for the panel's buttons, all gated on
   `smartsClaudeManager.patchEnabled`. `readSizes()` / `readToggles()` build the desired state from VS
   Code configuration; `readFeatureDefaults()` supplies per-feature on/off defaults.

### Chat-enhancement features — a separate injection layer

`behaviorFeatures.<id>.ts` (17 files — `faro`, `reply`, `googlesearch`, `search`, `datetime`,
`askquestion`, `userstyle`, `blockquote`, `copybuttons`, `codeblock`, `toc-export-scroll`, `askcollapse`,
`autocontinue`, `draftsave`, `usernav`, plus `behaviorToolbar.ts`/`behaviorBootstrap.ts` for shared
infrastructure) are
fundamentally different from a `PatchPoint`/`TogglePoint`/`InjectPoint`: those swap an *existing* value
already in the bundle, these add *new* client-side JS/CSS behavior that doesn't exist in the stock bundle
at all.

- **`behaviorFeatures.ts`** is the registry — each `behaviorFeatures.*.ts` module calls
  `registerFeature({id, label, js, css})` at import time; `patcher.ts` imports this registry and folds
  every feature's `js`/`css` into one `chatEnhancements` `TogglePoint`.
- **`behaviorInject.ts`** assembles the final injected block: one marker-tagged inline `<script nonce>` +
  one `<style>` block, spliced into `webview/index.js`/`index.css` right before `</body>`/the CSS end —
  never separate asset files with `<script src>` (the webview's CSP is `script-src 'nonce-${u}'` only).
  `escapeForTemplateLiteral()` doubles backslashes so injected text survives being re-embedded inside
  Claude Code's own outer template-literal source.
- **`behaviorBootstrap.ts`** is the shared runtime every feature's IIFE registers against
  (`window.__ccOnChatDoc`) — `document` already *is* the chat document in this VS Code webview target (no
  nested iframe to hunt for).
- Per-feature on/off is controlled **only** by its own `smartsClaudeManager.feature.<id>` VS Code
  setting, surfaced as a checkbox in the settings panel — there is no in-chat toggle UI and no master
  switch for the whole pack (it is always injected).

Full behavioral detail (Faro/CSP, DraftSave's storage-key history, AutoContinue's false-fire guards, and
more) is documented feature-by-feature further down in this file, under
["Chat-Enhancement Features Architecture"](#chat-enhancement-features-architecture) — consult it before
touching a `behaviorFeatures.*.ts` file.

### `panel.ts` — two webview hosts, one shared renderer

`abstract class PatchWebviewHost` owns `html()` / `knobHtml()` / `featureHtml()` / `onMessage()` /
`update()` — the actual UI rendering and message-handling logic. Two concrete subclasses reuse it against
VS Code's two different webview surfaces (`vscode.WebviewPanel` and `vscode.WebviewView` expose the same
`.html` / `.postMessage` / `.onDidReceiveMessage` / `.cspSource` interface):

- **`PatchPanel`** — a floating editor-tab panel, opened via the `smartsClaudeManager.panel` command.
- **`PatchSidebarView`** — an Activity Bar-docked sidebar view (`registerWebviewViewProvider`), lazily
  resolved the first time its Activity Bar icon is opened.

When adding a new panel feature, add it to the shared base class — adding it to only one subclass makes
the sidebar and the floating panel silently diverge. Full layout/CSS detail is under
["Two Host Surfaces, One Shared Control-Surface Renderer"](#two-host-surfaces-one-shared-control-surface-renderer)
further down.

### `extension.ts` — activation/deactivation

`activate()` runs two one-time settings migrations (`migrateNamespaceRename()` for the pre-2.0.0
`claudeCodeUiPatch` → `smartsClaudeManager` rename, `migrateLegacyKeys()` for pre-rename `chatDiff*` →
`chatDiffCard*` keys), then constructs `Patcher`, `StatusBar`, and `PatchSidebarView` and registers the
`smartsClaudeManager.panel` command. `deactivate()` is a deliberate no-op — see
["`deactivate()` Is a Pure No-Op"](#deactivate-is-a-pure-no-op--it-never-reverts-the-on-disk-patch)
below for why.

### `statusBar.ts`

A single status-bar item (`aA`) showing a hover summary of patch state; click opens the panel.

### Configuration surface

Every setting lives under the `smartsClaudeManager.*` namespace in `package.json`'s
`contributes.configuration.properties`. When adding a new config key, it must be declared in
`package.json` **and** wired into the matching `PATCH_POINTS`/`TOGGLE_POINTS`/`INJECT_POINTS` table in
`patcher.ts` (with a shipped default matching the JSON schema default) for the panel's drift-detection to
work correctly — see also
["Shipped Default vs Native Restore Value"](#shipped-default-vs-native-restore-value--owned-by-smarts-app-vscode)
further down.

**EVERY new `PATCH_POINT`/`TOGGLE_POINT`/`INJECT_POINT` id MUST ALSO be added to the `KNOB_ORDER` array in
`patcher.ts` (near the top), in its intended panel position — this is a THIRD required wiring step, not optional.**
`snapshot()` sorts every knob by `knobOrder(id)`, and `knobOrder()` returns `KNOB_ORDER.length` (i.e. sorts to
the VERY END) for any id NOT in the list. So a new point that is declared in `package.json` and wired into its
`patcher.ts` table but forgotten in `KNOB_ORDER` still *works* and still *renders* — it just silently appears at
the bottom of its section instead of where intended, with no error anywhere. **Real incident (this chat):** the
new `userMessageSize` INJECT_POINT was fully wired and functional but omitted from `KNOB_ORDER`, so it landed at
the very end of the Chat Panel instead of after `diffCard`; fixed by inserting `"userMessageSize"` after
`"diffCard"` in `KNOB_ORDER`. **Self-check when adding any point:** did I touch `KNOB_ORDER` too? If not, the knob
is mis-ordered. The section a knob shows under is its `section:` field (`"Chat Panel"`/`"Plan Preview"`); its
position WITHIN that section is its index in `KNOB_ORDER` — the two are independent.

**A newly-added knob does NOT appear (or its ordering/reload-button change does not take effect) until the panel
is running the freshly-COMPILED build — the running Extension Development Host (F5) or installed copy keeps its
old `out/` until reloaded.** This is the same "a disk change never live-updates an already-open webview" fact
`smarts-app-vscode` → `module/host-lifecycle.md` owns, applied to the panel itself: after `npm run compile`,
reload the F5 host (or reinstall the `.vsix`) before concluding a new knob "isn't showing" or its
"Save-and-reload button doesn't appear." **Real incident (this chat):** the new `userMessageSize` knob's
reload-pending path was verified correct by a real test (changing the knob flips `needsReload` so the
Save-and-reload button shows), yet it looked broken live — solely because the open panel was still the
pre-compile build; it was never a code bug.

**Every INJECT_POINT that scopes a font-size/family to ONE side of the chat re-reads its own CSS-module hash at
patch time from a stock anchor rule, exactly like the agent-body `chatHistorySize` point.** The user prompt
bubble is `.userMessage_<hash>` / `.userMessageContainer_<hash>` (one shared hash); `userMessageSize`
(`smartsClaudeManager.userMessageFontSize`) sizes the user body only, the deliberate mirror of `chatHistorySize`
which sizes only the agent body (`.root_<hash>`) and intentionally leaves user messages native. The two knobs
are independent by design — "Agent response" and "User message" in the Chat Panel. Anchor via `USER_MSG_HASH_RE`
/ `userMessageSelector()`; if the anchor is gone the point leaves the file native (`if (!sel) return c`), so a
Claude Code re-minify that renames the hash degrades to native rather than corrupting the bundle.

## This Extension Must Work in EVERY VS Code-Based IDE, Not Just Plain VS Code — `extensionsDirs()` Is the Universal Discovery Mechanism

**`patcher.ts`'s `extensionsDirs(context)` resolves the running host's real extensions folder via `context.extensionUri` FIRST — this is the one mechanism that already works correctly no matter which VS Code-family fork is running this extension (VS Code, VS Code Insiders, VSCodium, Cursor, Windsurf, Trae, Antigravity IDE, …), with zero hardcoding.** A hardcoded fallback list (`.vscode`, `.vscode-insiders`, `.vscode-oss`, `.antigravity-ide`, `.antigravity`, `.cursor`, `.windsurf`, `.trae`, `.vscodium`) exists only for a DEFENSIVE secondary scan (e.g. Claude Code installed under a different IDE-family profile than the one this extension itself runs under) — each entry is only used if its `extensions/` folder actually exists on disk. Never assume that list is exhaustive; add a genuinely new fork's folder name there when discovered.

**This machine's VS Code profile paths are JUNCTIONS onto D: (verified live 2026-08-06):** `C:\Users\Administrator\.vscode` → `D:\Machine\Develop\Platform\code.visualstudio.com\Settings\App\.vscode`, and `%APPDATA%\Code\User` → `D:\Machine\Develop\Platform\code.visualstudio.com\Settings\ALL\User` (a companion `.appgo` pointer file sits beside the `User` junction naming the target). ## A Genuinely OLDER Extension Version Can Stay Permanently Active — Check `extensions.json`'s `pinned` Field, Never Assume the Newest `.vsix` Wins

**SCOPE WARNING — this whole section describes a GENERIC VS Code-family install-state fact that was true back when this project was still sometimes run from an installed `.vsix`. It does NOT apply anymore: this project's dev workflow is now EXCLUSIVELY F5 (see the section above), so `extensions.json`/`pinned`/`.obsolete` are never read for `smarts-claude-manager` here. This section is KEPT only as (a) the historical record of the incident and (b) a generic fact worth knowing for a DIFFERENT, non-F5 VS Code-extension project — never re-apply this diagnosis to THIS project.**

**Real incident, this project, 2026-07-14/15:** after installing `smarts-claude-manager` v2.0.61, the panel kept showing **v2.0.24** — a version from many commits earlier, missing the `patchEnabled` gate, the EPERM-retry fix, the Faro/CSP patch, and the whole top-of-panel Enable/Disable toggle. Six version folders coexisted on disk (`...2.0.19` through `...2.0.61`); every one of v2.0.30 through v2.0.61 was correctly marked in `.obsolete`, yet the extension host kept activating v2.0.24 regardless of "Reload Window," a genuinely fresh chat panel/tab, or even a full app quit-and-relaunch. Root cause, found by reading Antigravity IDE's own `<extensions-root>/extensions.json` (the authoritative install registry): the `zeyutang.smarts-claude-manager` entry had **`"metadata": {"pinned": true, ...}`** pointing at the `...-2.0.24` folder — a VS Code-family install-state fact **entirely outside this project's own source code** (grep confirms nothing in `src/*.ts` ever reads or writes `pinned`/`installedTimestamp`/`extensions.json`). No amount of reinstalling a newer `.vsix` overrides a pinned entry; VS Code keeps reactivating the pinned version until it is explicitly unpinned or uninstalled through the Extensions UI.

- **The diagnostic tell:** the visibly-running panel shows an old feature set (missing checkboxes, old section headings like "Chat Enhancement Features" instead of "Chat Features") that doesn't match the newest committed UI — that mismatch, cross-checked against the version pill, is the signal to stop assuming "the newest install must be active" and go read `extensions.json` directly.
- **The fix is user-side, not code-side:** uninstall the stuck version via the Extensions view (gear icon → Uninstall) — never hand-edit `extensions.json`'s `pinned`/`installedTimestamp` fields directly, since that file is VS Code's own live state and an external edit risks corrupting the registry the running host has already loaded into memory — then fully restart the IDE and reinstall the intended `.vsix` via **Install from VSIX...**.
- **When a stuck old version is suspected, `git diff <old-version-tag/commit>..HEAD` is the right tool to rule OUT a code regression before chasing an install-state bug** — diffing this project's v2.0.24 commit (`4df7db8`, the parent of `9498822` which bumped to 2.0.25) against `HEAD` showed only deliberate feature additions (the `patchEnabled` gate, `deactivate()`'s file-revert, the CSP/Faro patch, the top-toggle UI) — nothing that would explain a newer version failing to activate, which is exactly the evidence that pointed at VS Code's own install-state instead of a source regression. The general form of this diagnostic — comparing an old-but-working version's tag/commit against the latest working-tree code file-by-file to isolate a regression, with the fallback of temporarily restoring specific old-version code into the working tree to unblock the user — is owned by `smarts-app-all` → `module/version-regression-diagnosis.md`; this project-local note only records the concrete incident and its resolution here.
- **This `pinned: true` behavior is a general VS Code-family fact, not Antigravity-IDE-specific — it recurred identically in plain VS Code** (2026-07-15): `zeyutang.smarts-claude-manager` showed `"pinned": true` in `~/.vscode/extensions/extensions.json` pointing at v2.0.63 (that time, correctly the newest version, so pinning itself wasn't the bug — but it confirms every VS Code-family host can pin an extension entry independent of which version is newest on disk). Always check `extensions.json`'s `pinned` field on ANY VS Code-family host when a version mismatch is suspected, not just Antigravity IDE.

## `deactivate()` Is a Pure No-Op — It NEVER Reverts the On-Disk Patch

**`extension.ts`'s `deactivate()` does nothing beyond letting VS Code clean up registered disposables — it deliberately never calls `Patcher.restoreFilesOnly()` or anything else that touches the on-disk bundle.** This went through two iterations, and the current, correct one is a pure no-op:

1. **Originally**, `deactivate()` was a comment-only stub (matching v2.0.24) — the only revert path was the panel's own toggle/button.
2. **Then**, to fix a real reported bug ("patch extension remove qilinsa ham patch applied turibdi" — the patched UI stayed active even after uninstalling/disabling this extension without first clicking the panel's toggle), `deactivate()` was changed to unconditionally call `Patcher.restoreFilesOnly()` (a synchronous, side-effect-free method reverting `extension.js`/`index.css` to native) via a module-level `activePatcher` reference.
3. **This turned out to be a WORSE regression**, discovered by directly diffing this extension's own working v2.0.24 commit against a later, misbehaving HEAD (per the general technique now owned by `smarts-app-all` → `module/version-regression-diagnosis.md`): `deactivate()` fires **identically** for an ordinary window reload and for a genuine uninstall/disable — VS Code's own API gives no way to tell them apart (confirmed against `microsoft/vscode#110034`, still open). So the unconditional revert reverted the patch on **every single reload**, not just a real removal, and whatever activated next had to re-apply it from scratch — a screenshot or check taken in that narrow revert-then-reapply window looked exactly like "the patch keeps failing/chala apply," when the revert itself was the actual bug. **Reverted back to a pure no-op**, exactly matching v2.0.24's behavior, which was rock-solid specifically because it never touched the disk except on activation.

**The accepted tradeoff (same one v2.0.24 always had):** a user who uninstalls/disables this extension **without** first using the panel's own Enable/Disable toggle leaves the patched bytes on Claude Code's disk until either they reinstall and toggle it off themselves, or Claude Code's own next auto-update overwrites `extension.js`/`index.css` natively anyway (which happens routinely). This tradeoff is deliberate and was reconfirmed directly by the user — stability of the common case (the patch staying correctly applied across ordinary reloads) outweighs cleanly reverting the rare case (an uninstall with no prior toggle click).

**Re-researched 2026-08-06 (real web research, cited in `extension.ts`'s own `deactivate()` comment): still no VS Code API closes this gap.** `onWillUninstall`/`onDidUninstall` do not exist; `vscode.extensions.onDidChange` cannot help (an uninstalled extension's own code no longer runs); the `package.json` `"vscode:uninstall"` script hook exists but ALSO fires on a plain extension UPDATE (`microsoft/vscode#72375`), which would reintroduce the revert-then-reapply flicker; a delayed-check `setTimeout` dies with the extension host context. **The accepted industry pattern, confirmed against real patcher-style extensions (`be5invis/vscode-custom-css`, `lehni/vscode-fix-checksums`): no auto-revert on uninstall, only a manual restore command — exactly what this extension's top-of-panel toggle already is.** Do not re-attempt an auto-revert-on-deactivate without new API evidence.

**Testing `applyPatch()`/`restorePatch()` follows the generic disk-mutating-apply/restore test pattern owned by `smarts-app-vscode` → `module/host-lifecycle.md`** (establish a clean baseline via a pre-clean `restorePatch()` + a second-call idempotency check before diffing; a plain-Node test `require()`ing the compiled `out/patcher.js` outside the extension host uses a minimal `vscode` stub via `Module._resolveFilename` and must pass realistic config/toggles). **"Disable patch never sticks" was a REAL, deterministic ordering bug inside `restore()` itself (root-caused and fixed 2026-08-06, commit 928b250): `setPatchEnabled(false)` was the LAST element of `restore()`'s parallel `Promise.all` settings-reset batch — every earlier reset write fired `onDidChangeConfiguration` → `autoApply()`, which read `patchEnabled` while it was STILL `true` and re-applied the ALWAYS_ON toggles (`chatEnhancements`, `faroCsp`) into the bundle `restorePatch()` had just reverted.** The window then reloaded with `patchEnabled: false`, so nothing ever cleaned the re-injected patch again — settings said "disabled" while the bundle stayed patched. Not a marginal race: `cfg.update` writes land in launch order, so patchEnabled-last made it fire on every single click. **The on-disk fingerprint that proved it:** after each Disable click, `extension.js` held exactly the always-on markers (`ccup-behavior`, `connect-src …grafana`) plus default-true toggles (`ccup-theme`), with every px/size patch correctly at stock — precisely what a post-restore `autoApply()` re-applies when all settings read stock but `readToggles()` forces the ALWAYS_ON ids true. **The fix: `restore()` now awaits `setPatchEnabled(false)` FIRST, before `restorePatch()` and before the resets** — every reset-triggered `autoApply()` then reads `false` and no-ops. **The general lesson for any future `Promise.all` of `cfg.update` calls whose config-change listeners take state-dependent actions: the write that GATES the listener's action must land first, awaited alone — never ride in the same parallel batch as the writes that trigger the listener.** (Diagnosed via a stub-driven manual `restorePatch()` run — the project's own documented `Module._resolveFilename` vscode-stub pattern — which reverted the live bundle perfectly, proving the revert logic sound and pointing the investigation at what runs AFTER it.)

**"Chala apply bo'lmoqda" (partial patch application) was a REAL bug — Windows transiently locks a just-updated Claude Code extension's files, and a single file's write failure used to abort the WHOLE patch batch, silently leaving later files completely unpatched.** Root-caused from a real error toast: `EPERM: operation not permitted, rename '...extension.js.<pid>.<n>.tmp' -> '...extension.js'`, firing right after Claude Code auto-updated to a fresh version (a newly-extracted extension's files are briefly held open by Windows Defender/an indexer/the extension host's own read — almost always transient, gone within milliseconds). Two compounding defects: (1) `writeFileAtomic()` had zero retry — the very first `EPERM` threw immediately; (2) `applyPatch()`/`restorePatch()`'s single `for` loop over `extension.js` → `webview/index.css` → `webview/index.js` had no per-file error isolation, so `extension.js` (patched first, holding the chat-enhancements script + `faroCsp`) failing aborted the loop before `webview/index.css` (the behavior-CSS block — "interface looked dim, CSS wasn't loading") or `webview/index.js` (the diff-card toggles — "some features work, some don't") were ever reached, even though their content changes had already been computed and were ready to write. Fixed: `writeFileAtomic` now retries `EPERM`/`EBUSY`/`EACCES` on the rename step up to 5 times with a 50/100/150/200ms backoff before giving up; separately, each file's write in `applyPatch`/`restorePatch` is wrapped in its own try/catch, so one file's persistent failure is recorded in the returned `PatchReport.failed` (`{file, error}[]`) and reported to the user by name via `autoApply()`, while every OTHER file still gets its own write attempt regardless. Verified via a real scratch-copy test simulating both a transient lock (recovers automatically after 2 failed retries) and a persistent one (the locked file is correctly reported as failed while every other file still gets patched on disk) — `.claude/Chat Patch Extend/Tests/partial-apply-fix/run.mjs`, 6/6 assertions.

## Chat-Enhancement Features Architecture

The chat-webview behavior features (Faro, Reply, Google Search, Search, DateTime, AskQuestion, UserStyle, Blockquote, CopyButtons, MultiSelect, CodeBlock, AskCollapse, UserCollapse, AutoContinue, DraftSave, UserNav, ForkConv, ForkInCopy, Toc, Export, Scroll, FileLinks, ModelInfo, EffortInfo — one `behaviorFeatures.<id>.ts` file each, registered into `behaviorFeatures.ts`'s registry, imported in `patcher.ts` in load/sweep order) are fundamentally different from every `PATCH_POINT`/`TOGGLE_POINT`/`INJECT_POINT` in `patcher.ts`: those swap an *existing* hardcoded value already in the bundle, whereas a chat-enhancement feature adds *new* client-side behavior that doesn't exist in the stock bundle at all.

**There is NO `notify` feature in this list, and there never will be one again — question/reply notifications (taskbar flash / toast / audio beep) are OWNED ENTIRELY BY A GLOBAL CLAUDE CODE CLI HOOK (`~/.claude/hooks/vscode-notify.mjs`), not by this extension.** A DOM-watching `behaviorFeatures.notify.ts` feature existed here through v2.0.107 (a "Notifications" panel section with 3 checkboxes: flash-on-ask, flash-on-complete, sound-on-complete) — it was **removed** because: (1) detecting "a reply just finished" by watching the chat DOM for a Stop button disappearing, or "a question was asked" by watching for a dialog element appearing, is fragile against any Claude Code bundle change with no way to notice a silent break; (2) its only "flash" mechanism, `vscode.window.showInformationMessage()` relayed through the `openExternalBridge.ts` `ccNotify` message type, never actually produced a visible taskbar effect in real testing, and had no way to target one specific window among several open VS Code windows/tabs. The replacement hook reacts to Claude Code's own real `Notification`/`Stop` hook events (an authoritative, DOM-independent signal that fires whether or not this extension's patch is even applied) and drives the OS directly: it detects whether the session is running inside a VS Code window at all via the `VSCODE_PID` env var (present only when `claude.exe` was spawned by VS Code itself, e.g. from `~/.vscode/extensions/anthropic.claude-code-*/resources/native-binary/claude.exe` — absent for a plain terminal/global-npm-install session, e.g. `~/.ai/node/node_modules/@anthropic-ai/claude-code/bin/claude.exe`, where the hook silently no-ops since there is no window to notify), then — for `"wintop"`/`"flash"` — calls a real Win32 `SetForegroundWindow()` (combined with the documented `AttachThreadInput()` foreground-lock workaround, the same trick AutoHotkey's own `WinActivate` uses) to fully activate the correct window, confirmed working via real, user-observed testing; `node-window-manager`'s own `bringToTop()` was tried FIRST and only changed Z-order without visibly stealing focus. Full mechanism, action meanings, and config schema: `~/.claude/CONFIG.md`'s `vscodeNotify` section. Do not re-add a Notify feature or a Notifications panel section to this extension — if a future request wants per-event/per-action control over these notifications, that control lives in `~/.claude/config.json`'s `vscodeNotify.events` map, not in this project's `package.json`/`panel.ts`.

**`multiselect` (`behaviorFeatures.multiselect.ts`) docks a checkbox as the FIRST child of CopyButtons' own `.cc-copy-group` row (the same row ForkInCopy docks its button into as the LAST child) on every assistant OUTPUT message, plus a toolbar "Copy selected" action that batch-copies every checked reply's content as one combined Markdown or HTML block (plain click = Markdown, shift-click = HTML).** It never re-derives its own DOM→text extraction — instead, `copybuttons.ts`'s `init()` now also exposes `window.__ccCopyButtons = { markdownOf, htmlOf, contentRoots }` (mirroring the export feature's own `window.__ccExport` pattern in `toc-export-scroll.ts`), and MultiSelect's `copySelected(format)` calls `markdownOf(msgEl)`/`htmlOf(msgEl)` on each selected message through that shared API — so both features always agree on what "a message's content" means, and a future extraction-logic fix (like the `contentRoots()` first-match-only bug documented above) automatically benefits both. Selection state lives in a `Set` keyed by element identity (pruned lazily against `document.body.contains()` so a React-unmounted message can never linger selected), never a fixed index or count, and toolbar-click reads `selList()` sorted into document order before joining. Toggleable via `smartsClaudeManager.feature.multiselect` (default on, requires `feature.copybuttons`), loaded in `patcher.ts` immediately after `copybuttons`. Real-DOM regression test: `tests/multiselect.test.mjs` (loads the real CopyButtons + MultiSelect injected scripts in jsdom, builds two output messages, checks both boxes, drives the real toolbar click, and asserts the clipboard fallback receives both messages' combined content in document order — plus a shift-click HTML case and an uncheck-shrinks-selection case).

**The FOOTPRINT toolbar-button class of bug — shipped THREE separate times; `tests/footprint.test.mjs` now guards the whole class.** `behaviorBootstrap.ts`'s `FOOTPRINT` map is the single central mechanism that CSS-hides a disabled feature's DOM, and a feature that registers a SHARED-TOOLBAR button (via `behaviorToolbar.ts`'s `__ccToolbar.add()`, which renders `[data-cc-tool="<id>"]` chips) needs its FOOTPRINT entry to actually match that rendered button — a selector that only covers the feature's per-message UI silently leaves the toolbar chip visible when the feature is toggled off. Recurrences: (1) `forkincopy` had no FOOTPRINT entry at all (fixed `14b5bc6`); (2) `multiselect`'s entry hid only `.cc-multiselect-chk`, never the toolbar chip — reported live as "checkbox off but the Select-replies button still shows" (fixed `eba4015`); (3) `scroll-bottom` never received its `.cc-scroll-bottom` class after `add()` (only `scroll-top` got classed), so scroll-off hid ⤒ but left ⤓ visible (same commit). **The rule going forward: a toolbar-registering feature's FOOTPRINT entry targets the button by its stable `[data-cc-tool='<id>']` attribute (which the toolbar itself guarantees), never only by a class the feature must remember to add.** `tests/footprint.test.mjs` enforces this for every toolbar-registering feature — it runs the REAL `BOOTSTRAP_SOURCE` + `TOOLBAR_SOURCE` in jsdom, renders real buttons through the real `add()` path, and asserts each feature's OFF state generates a hide selector that `el.matches()` the real button (verified to fail against the pre-fix bootstrap with exactly the reported symptom). Test-authoring gotcha it also encodes: the real bootstrap runs `setInterval(tick, 400)`, so every jsdom window must be closed in a `finally` — a failing assertion otherwise leaves timers alive and the `node --test` process hangs past its timeout instead of reporting the failure.

**`forkincopy` (`behaviorFeatures.forkincopy.ts`) is a SECOND, independent entry point to the same native "Fork conversation from here" action ForkConv's own left-docked button already exposes — added ADDITIVELY, per explicit request to keep ForkConv's original button in place rather than relocate it.** It docks a fork button as the LAST child of CopyButtons' own `.cc-copy-group` row (the time+Markdown+HTML row, reusing its `cc-copy-btn` class so it matches exactly) on every assistant OUTPUT message — never creating its own row. Toggleable via `smartsClaudeManager.feature.forkincopy` (default on, `markdownDescription` notes it requires `feature.copybuttons`), independent of ForkConv's own toggle — both can be on, off, or mixed.

**Real incident (2026-07-26) — the button never appeared at all on a real, freshly-opened chat, and the root cause was a wrong assumption about the live DOM shape, not an install/version issue.** `precedingUserMessage()`'s FIRST implementation only searched `stampedMessages()` (the `[data-cc-dt-time]`-stamped anchor set) for a distinct, earlier SIBLING entry classified as a user message — but `copybuttons.ts`'s own `contentRoots()` comment already documents that a live `turn_…` OUTPUT wrapper NESTS the user prompt bubble (`userMessageContainer_…`) INSIDE the same stamped element as the assistant's own response, rather than the user/output being two separate, sibling-level stamped entries. For a 1-exchange chat this means DateTime stamps exactly ONE element for the whole turn, not two — so the sibling-only search had no distinct "preceding" entry to ever find, and `ensureButton()` silently no-opped every time (`existing`/`userEl` both falsy, no diagnostic branch hit). **Diagnosed via real, live Faro sweep-diagnostic evidence** (`[cc-forkincopy] sweep stampedCount=1 outputCount=1 attachedCount=0`, added specifically to prove this rather than guess at it) confirming exactly one stamped element existed for the visibly-two-message chat — the concrete signal that pointed straight at the nested-vs-sibling DOM-shape mismatch. **Fixed** by having `precedingUserMessage()` check TWO ways, in order: (1) NESTED — `outputEl.querySelector([class*='userMessageContainer'],[class*='userMessage'])`, i.e. search *inside* the output element itself first (the common, real case); (2) SIBLING — the original earlier-stamped-entry search, kept as a fallback for a DOM shape where the two really are distinct stamped elements. `forkFrom()` itself needed no change — it already called `userEl.querySelector(MSG_ACTIONS_SEL)`, and a nested `userMessageContainer_…` bubble carries its own "Message actions" trigger exactly like ForkConv's own (confirmed-working) `findUserMessages()` target does. Real-DOM regression test: `tests/forkincopy.test.mjs` — rewritten to cover THREE DOM shapes: (1) the real NESTED shape (the actual bug scenario — a single `turn_` wrapper containing both the user bubble and the response), (2) the SIBLING fallback shape, (3) no preceding/nested user message at all. Confirmed via this correct method: the injected script (both in general and the currently-installed bundle) is syntactically valid — there was no real bug. When a future "zero `[cc-*]` console lines" report needs static verification, use the evaluated-template-literal method (slice used as-is, never re-escaped), not a raw-source check, or it will manufacture phantom syntax errors.

Discovered while writing a real end-to-end test against a scratch copy of this machine's own live installed extension (see [Every claude-webview change is tested only against a disposable scratch copy](#chat-composer-font-size--two-stacked-elements-share-one-hash-patching-only-one-is-invisible) above): the scratch copy was already patched by a prior install of this same extension, and `behaviorPresent()` returning `true` on it was correctly reporting "patchable," not incorrectly reporting "already injected" — the test had to normalize via `removeBehaviorScript()` first and then check `BEHAVIOR_MARKER` directly to establish a genuinely native baseline before testing a fresh `applyBehaviorScript()` call.

## Chat Composer Font Size — Two Stacked Elements Share One Hash; Patching Only One Is Invisible

The chat message-input box (composer) is actually **two stacked elements sharing one CSS-module hash**,
not a single `<textarea>`: the real `contenteditable` div (`role="textbox"`, `aria-label="Message input"`,
className `messageInput_<hash>`) is painted **invisible** (`color:#0000` in the stock CSS — it exists only
to hold the caret/selection and receive input events), while a sibling `aria-hidden` div, className
`mentionMirror_<hash>`, is positioned absolutely on top and is what **actually renders the visible text**
(including @-mention highlighting). **A patch that only sizes `messageInput_<hash>` changes the invisible
layer's metrics but leaves the visible text's size untouched** — confirmed live: the first cut of this
knob patched `messageInput_<hash>` alone, and the user reported exactly this symptom ("korinmaydigan
fontning size ozgarvotti, korinadigan esa ozgarmadi" — the invisible font's size changed, the visible one
didn't). Both classes share the same hash suffix as the third sibling rule `messageInputContainer_<hash>`,
so the fix sizes **both** together in one rule. Claude Code's own CSS sets no `font-size` on either, so
they silently inherit the webview's base font-size (~13px). Because there is no existing numeric value to
regex-swap, the `chatComposer` `PATCH_POINT` (`patcher.ts`, `webview/index.css`) follows the exact same
append pattern as `chatCode` (the code-block font point): it appends a marker-tagged
`/*cc-ui-patch:chatComposer*/.messageInput_<hash>,.mentionMirror_<hash>{font-size:<px>px !important}`
line, re-reading the hash at patch time from the stock `.messageInputContainer_<hash>{...}` rule so it
survives a re-minify that changes the hash. Exposed as `smartsClaudeManager.chatComposerFontSize` (default
14px; `originalPx: 13` is the true native/inherited stock, used only for the restore-to-stock path —
setting the knob to exactly 13 removes the marker line entirely rather than writing a redundant `13px
!important`). Verified end-to-end against a scratch copy of the real installed extension: apply
writes/updates the marker (both selectors) in place (no duplicates across repeated value changes), and
restore reverts `webview/index.css` byte-for-byte to baseline. **The lesson for any future
composer/contenteditable patch point in this project: always check for a sibling mirror/overlay class
sharing the same hash before assuming the element you found in the DOM inspector is the one that's
actually visible** — a `color:#0000`/`visibility:hidden` rule on the "obvious" target is the tell.

## Chat Features Checkboxes Reuse the SAME `.switch` Pill-Toggle Component as Chat Panel/Plan Preview Knobs

The Chat Features grid (`featureHtml()` in `panel.ts`) renders each feature row as `<button class="switch">`
— the identical track+thumb pill component the Chat Panel/Plan Preview knob toggles and the top-of-panel
Enable/Disable-patch switch already use — not a plain `<input type="checkbox">`. Per explicit user request
(a screenshot comparing the two: knob switches styled correctly, Chat Features still plain checkboxes), the
component was unified so every on/off control in the panel looks identical. Client-side wiring mirrors the
knob-toggle pattern exactly: a `featureToggle` click command (optimistic flip via `setToggleBtn()`,
`pendingFeature` tracking the last-sent value until the `sync` echo confirms it), replacing the old
`change`-event checkbox handler.

**A real bug shipped in the first cut and was caught live by the user: the switches rendered as bare,
unstyled buttons — a floating thumb with no visible green track — because the switch's reset/layout CSS
was scoped ONLY to `.knob .switch`, never to a parent-agnostic `.switch` selector.** `.feature-row` is not
`.knob`, so a `<button class="switch">` inside a feature row inherited none of `display:flex;
background:none; border:none; padding:0` and fell back to native browser button chrome (its own padding/
border/background), which is exactly what broke the layout. **The fix, and the general lesson for any
future reuse of the `.switch` component under a new parent selector: give the shared component ONE
parent-agnostic base rule (`.switch { display:flex; background:none; border:none; padding:0; ... }`) that
applies regardless of ancestor, and let each parent context (`.knob .switch { width:100% }`, `.feature-row
.switch { width:34px; margin-left:16px }`) ONLY ever adjust width/spacing on top of that base — never
re-scope the base reset itself to one specific parent.** A component's reset/layout rule scoped to only its
first-known usage silently breaks the moment the same class is reused under a different container; always
check the CSS for a component being reused before assuming its existing rule is parent-agnostic.

A second, unrelated mistake was caught in the same fix: an inline code comment describing this bug used a
backtick around a CSS selector (`` `.feature-row .switch` ``) inside `baseCss`'s own JS template literal —
tripping the exact backtick-inside-a-template-literal hazard `smarts-app-vscode`'s own invariant warns
about (a stray backtick silently terminates the string early). `tsc` caught it immediately as a syntax
error at compile time rather than a silent runtime break, but the lesson holds: never put a raw backtick in
a comment inside `baseCss`, even to reference a CSS selector — write the selector without backticks instead.

## Two Host Surfaces, One Shared Control-Surface Renderer

The control panel (font-size knobs, toggles, the Chat Features grid) is hosted on TWO separate VS Code surfaces that share one rendering/message-handling implementation:

- **`PatchPanel`** — a floating editor-tab `WebviewPanel` (`vscode.window.createWebviewPanel`), opened via the `smartsClaudeManager.panel` command (Command Palette or status-bar click).
- **`PatchSidebarView`** — an Activity Bar-docked `WebviewView` (`vscode.window.registerWebviewViewProvider`, view id `smartsClaudeManager.sidebarView`, icon `media/activitybar-icon.svg`), resolved lazily the first time the user opens it from its own Activity Bar icon.

Both extend the abstract `PatchWebviewHost` base class in `panel.ts`, which owns `html()`/`knobHtml()`/`featureHtml()`/`onMessage()`/`update()` — `vscode.WebviewPanel.webview` and `vscode.WebviewView.webview` expose the identical `vscode.Webview` interface (`.html`, `.postMessage`, `.onDidReceiveMessage`, `.cspSource`), so one implementation drives both hosts; only creation/reveal/lazy-resolution differs per subclass. When adding a new panel feature (a new command, a new message type), add it to the shared base, not to one subclass only — otherwise the sidebar and the editor-tab panel silently diverge.

**The panel must work at TWO very different widths — the wide editor-tab panel AND the Activity Bar sidebar's real narrow width (~250-350px)** — a single fixed-width knob-row design (label + a 168px `▼`/▲`/px control group) cannot fit the sidebar at all, and a horizontal-scroll fallback was tried and rejected (it left the controls clipped to unusable slivers). The actual fix is a real `@media (max-width: 500px)` breakpoint in `baseCss`: `.feature-grid`/`.section-grid` collapse to a single column, and the bottom `.actions` row stacks its buttons full-width (one per row, taller with a smaller icon/font) instead of sitting side-by-side (a multi-up layout truncated a footer button's label down to unreadable slivers). Each `.knob` row stays on ONE line even here — the `▼`/`▲` spinner buttons were replaced with a plain `<input type="number">`, and in the narrow view the input/switch is moved BEFORE the label via CSS `order` (not DOM reordering), with the label truncating via `text-overflow: ellipsis` instead of wrapping to a second line. When changing the panel's layout CSS, always check BOTH the wide (`section-grid`'s 3-column shape) and narrow (`@media (max-width: 500px)`) rules — a change to one that isn't mirrored in the other will look fine in the editor tab and break in the sidebar, or vice versa. Two universal webview-CSS-authoring pitfalls hit while building this panel (a `@media` block must be the LAST rule in a stylesheet, and `baseCss`'s backtick-delimited template literal must never contain a raw backtick, even in a comment) are owned by the `smarts-app-vscode` skill's `module/webview-css-authoring.md` — invoke it for any future CSS-cascade or template-literal-authoring issue, in this project or any other.

**The footer `.actions` row holds up to THREE buttons, in this fixed order: Restore Last Applied → Open VS Code Settings → Reload window to apply changes (the last only rendered while a reload is pending).** The former "Fully Disable Patch"/"Enable Patch" footer button was REMOVED — its function now lives in the top-of-panel "Enable / Disable patch" toggle (see the patchToggle paragraph above); do not re-add it to the footer. "Restore Last Applied" (`.btn-green`, `data-cmd="discard"`) reverts uncommitted knob changes to the last-applied floor. The pending-reload action used to be a clickable banner in `.header-status` under the title; it was moved into the footer as its own button (`statusInner()` returns an empty string for the `needsReload` case, and `.header-status:empty` collapses its margin so no gap is left). Since `needsReload` is not part of `shapeOf()`'s structural-shape string (only `snap.supported`/`snap.version`/`snap.patchEnabled`/the knob-id list are), a reload-pending transition arrives as a lightweight `sync` postMessage rather than a full HTML re-render — the client-side `sync` handler therefore creates/removes the reload `<button>` element in place (`document.querySelector('.actions')`) rather than relying on the full-render HTML.

**The correct DevTools target for any `[cc-*]` console.log/console.error diagnostic is reached by right-clicking directly inside the chat panel/composer → Inspect Element**, which opens a separate devtools window scoped to that webview's iframe — NOT the main VS Code workbench console (`Help > Toggle Developer Tools`), which never shows `[cc-*]` feature logs. **AskCollapse (`behaviorFeatures.askcollapse.ts`) works around a stale AskUserQuestion suggestion chip visually persisting across a VS Code editor TAB switch.** Reported live: a floating suggestion card ("yana qanday model/engine/platform") from one tab stayed visible, overlapping the composer/toolbar, of a DIFFERENT tab that became active — clearing only after switching away and back once more. Root cause is a VS Code webview suspend/resume rendering artifact, not a DOM node our script owns or creates: a hidden tab's webview is throttled, so a suggestion chip mid-animation/reposition at the moment the tab loses visibility can freeze mid-frame and repaint stuck once the frame resumes on whichever tab is active then. The fix is NOT to hunt for "the" stale element by identity (there is none — it is a frozen paint, not leaked state) but to force a browser reflow of any floating (`position:fixed`/`absolute`), question-scoped element the moment `document.visibilityState` becomes `"visible"` again (`resweepOnVisible()`, wired via a `visibilitychange` listener in `init()`) — toggling `display:none` then back and reading `offsetHeight` in between forces the engine to recompute layout/paint instead of reusing the frozen frame. This is a workaround for a rendering artifact, not a root-cause fix (the true cause lives in VS Code/Chromium's own webview compositor); if it stops being sufficient, the next escalation is a forced repaint of the whole document (a `transform` no-op toggle on `document.body`) rather than just the individual floating element.

**UserCollapse (`behaviorFeatures.usercollapse.ts`) adds an "Expand message"/"Collapse message" MENU ITEM to Claude Code's native "Message actions" popup — it is NOT a persistently-docked floating icon, after two docking attempts both failed for different reasons.** History, in order:
1. **Docked beside the native `expandButton_<hash>`/`collapseButton_<hash>` control itself** (which is `position:absolute; bottom:0; right:0` on the expandable-content box, only rendered on hover — see the `SHOW_MORE_MARKER` comment in `patcher.ts`). Reported live: the icon floated in the middle/bottom of the message instead of near the top.
2. **Docked as a SIBLING of "Message actions"'s own container** (matched by `button[title='Message actions']`, a stable human-readable attribute, not a hash-suffixed class), reasoning that "Message actions" is `uYe`, a live React component that re-renders and reconciles its own children on every hover transition — a manually-inserted node living INSIDE that container gets wiped as an "unrecognized child" the moment hover state changes, so docking one level up (a sibling, not a child) was the fix for THAT specific failure mode. This was a real, confirmed bug and the fix was correct for it — but it was not the only problem.
3. **The icon was STILL completely absent, even on hover, even docked as a sibling** — confirmed via DevTools inspection: no button element existed at all. Root cause: Claude Code's OWN native "Show more"/"Show less" button (`oYe`'s `expandableContainer` component) is itself only added to the DOM while `l` (a `useState` hover flag, set by `onMouseEnter`) is true — it does not exist in the DOM AT ALL otherwise, hover or not, depending on exact timing/state. A persistently-docked icon anchored beside ANY element that is itself conditionally hover-mounted has nothing stable to anchor to in the common case; no amount of re-anchoring fixes this, since the problem is upstream of where the icon docks.

**The fix (current, shipped): abandon floating-icon docking entirely.** Add an "Expand message"/"Collapse message" row as the FIRST item of Claude Code's own native "Message actions" POPUP menu (alongside "Fork conversation from here", "Rewind code to here") — matched by class-name substring (`[class*='popup_']`, `[class*='popupOption_']`, `[class*='optionText_']`, mirroring `EXPAND_SEL`/`COLLAPSE_SEL`'s own convention), copying the FIRST real `popupOption`'s class list live so the injected item inherits the exact native font/padding/hover styling with no hash to hardcode. The popup only exists in the DOM while explicitly OPENED by a real click (not hover) — a far rarer, more deliberate re-render trigger than the "Message actions" button's own hover cycling, and a UI-idiomatic place users already look for "more actions on this message." Clicking the item proxies a real click onto whichever native `expandButton_`/`collapseButton_` is currently live (same mechanism as before), then closes the popup by dispatching a click back on the "Message actions" trigger. The native "Show more"/"Show less" text controls stay fully visible and untouched, exactly as the prior fix already established (per explicit user request, "oldingi show more/show less ni ham qoldiraqol") — the popup item is an ADDITIONAL shortcut, never a replacement.

**Lesson for any future feature that needs to persistently dock UI beside a native Claude Code element: verify the native anchor's OWN mount lifecycle first, not just its re-render behavior.** An element that is `position:absolute`-and-hover-only, or — worse — only EXISTS in the DOM conditionally (a `useState`-gated conditional render, not just a CSS visibility toggle), cannot host a persistently-visible docked sibling no matter how carefully the docking logic is written; the anchor itself must be always-present in the DOM (even if visually faded) for any docking strategy to work at all. When the only stable, always-mounted native anchor is a popup/dropdown TRIGGER rather than its otherwise-hidden target, injecting into the trigger's own POPUP CONTENT (which mounts deliberately, on click) is more robust than trying to dock beside the trigger itself.

**Verified for real against a disposable scratch copy of the installed extension** (never the user's live install): the injected script — extracted and unescaped via `behaviorInject.ts`'s own `currentBehaviorScript()` regex (never a naive `indexOf`-to-first-`</script>`, which can cut early on a literal `"</script>"` substring inside the escaped script's own comments) — is syntactically valid via the evaluated-template-literal method; the popup-item markers are present after apply; a second `applyPatch` call is idempotent (no `chatEnhancements on→on` content rewrite, only cosmetic gutter-CSS re-cleans); and `restorePatch` reverts `extension.js` byte-for-byte back to native, including the new popup-item code.

**Any `position:fixed` popup this project injects MUST compute its horizontal offset from a REAL composer element's `getBoundingClientRect()` — never a flat CSS value like `right:16px` — because this webview's raw CSS viewport can be noticeably WIDER than the composer's own visually-bordered box.** Both the TOC/Outline panel (`.cc-toc-panel`) and the Export menu (`.cc-export-menu`) in `behaviorFeatures.toc-export-scroll.ts` originally used `position:fixed; right:16px`, which is measured from the WHOLE CSS viewport — reported live via a screenshot with a red line marking the composer's real right edge: the popup floated well past that line, out in open empty space, clearly disconnected from the composer box it was supposed to relate to. The shared docked toolbar row (`behaviorToolbar.ts`, which inserts its chip buttons directly INTO the composer's own `[class*='inputFooter']` element rather than using `position:fixed`) stayed correctly aligned throughout, which is what made the discrepancy obvious — a real DOM insertion inherits the parent's actual layout position; a `position:fixed` element with a flat offset does not, and there is no guarantee in this webview that the CSS viewport's edge coincides with the composer's own edge. **The fix:** both panels now query `[class*='inputFooter']` (the same footer element the toolbar already docks into, spanning the composer box corner-to-corner) and compute `panel.style.right = (viewportWidth - footerRect.right) + "px"` — via a `positionPanel()`/`positionMenu()` helper called on open and on window resize while open — so the popup's right edge always matches the composer's real right edge, regardless of how much wider the raw viewport is. **This pattern generalizes to any future `position:fixed` UI in this extension:** never hardcode a `right`/`left`/`bottom` CSS value assuming it lines up with the composer or chat panel's own visual bounds — always measure a real, already-correctly-positioned anchor element (the composer footer, the toolbar bar, or the message list container) and compute the offset from its live bounding rect instead.

**DraftSave's storage-key history (ROOT-CAUSE FIXED — three options tried, Option 3 is what shipped):**

1. **Option 0 (root cause, historical) — `chatId()` originally read a `session=` query param that DOES NOT EXIST anywhere in this target's real webview URLs.** Every webview URL actually observed in this VS Code Claude Code build is shaped `index.html?id=<uuid>&parentId=<n>&origin=<uuid>&swVersion=<n>&extensionId=Anthropic.claude-code&platform=electron&...` — there is no `session=` param at all, only `id=` (per-webview-**instance**, confirmed to differ across multiple simultaneously-open chat panels). Because `chatId()` only recognized `session=`, it always returned `null`, so `draftKey()` was always `null` and both `saveNow()`/`restoreIfEmpty()` permanently no-opped — **DraftSave never actually saved or restored anything**, despite looking fully implemented in isolation.
2. **Option 1 (switch `chatId()` to read `id=` instead of `session=`) landed, then was CONFIRMED INSUFFICIENT by real user testing** ("DraftSave UMUMAN ISHLAMADI! reload webview and reload windiws da ham ishlamadi umumn yoqolib qoldi" — completely stopped working; Reload Webview AND Reload Window both lost the draft). `id=` genuinely regenerates on both a webview-only reload and a full window reload in this real build — the trade-off documented at landing time (works within a live tab session, not across any reload) turned out to be too narrow, since a reload is a common real-world case.
3. **Option 2 (`vscode.setState()`/`getState()` via a SECOND `acquireVsCodeApi()` call) is CONFIRMED UNSAFE and PERMANENTLY ABANDONED — it crashed the entire chat webview.** The temporary probe (`probeVsCodeApi()`) was live-tested and the real result was the chat panel crashing with "Something went wrong / Re-launch the extension to continue / Error rendering content: Encountered errors while disposing of store" — `acquireVsCodeApi()` can only be called once per webview; Claude Code's own extension code already calls it for its React/Redux store's postMessage/setState plumbing, and the second call throws during the chat webview's bootstrap, corrupting that store's init. **`acquireVsCodeApi()` must NEVER be called from any injected chat-enhancement script, under any circumstance** — this is the confirmed root cause of a full chat-panel crash, not a theoretical risk.
4. **Option 3 (SHIPPED) — a single GLOBAL localStorage key (`cc-draft:global`), not per-chat at all.** The insight that unblocked this: localStorage in this VS Code build is partitioned by webview TYPE/origin, not by webview instance, so it already survives every reload on its own — every earlier option's real bug was the volatile per-chat KEY, never the storage medium. A fixed, non-per-chat key sidesteps the whole "how do we get a stable per-chat id" problem, at the accepted cost of the draft not being chat-specific (switching chats can surface another chat's last draft). Two mitigations: (a) a `sessionStorage`-based best-effort "does this look like a reload of the same instance" guard (`looksLikeReload()`/`markInstanceLive()` — `sessionStorage`, unlike `localStorage` in this build, is scoped to the browsing context's own lifetime); (b) a 10-minute staleness TTL (`STALE_MS`) past which a saved draft is treated as expired and never restored. Every save/restore/clear/expire routes through the Faro Logging feature (module id `draftsave`) — length/metadata only, never the draft text.

## Every Commit Auto-Bumps the Version and Auto-Builds a `.vsix` — Owned by `smarts-app-vscode`

This project's `core.hooksPath` is set to its tracked `githooks/` folder (`git config core.hooksPath githooks`, a per-clone local setting a fresh clone must re-run once). `githooks/pre-commit` deterministically bumps `package.json`'s patch version and stages it into the same commit; `githooks/post-commit` then compiles and packages a fresh `.vsix` into `build/` for that version — no model/LLM involvement at commit time, and no manual version bump going forward. Both hooks are thin shims calling the shared canonical script `~/.agents/githooks/Auto Version Build.mjs`, reused by every VS Code extension project. The general convention (the shared-script design, the Windows `.cmd`-spawn + shell-quoting pitfalls already fixed in it, and how to wire this into a new project) is owned by the `smarts-app-vscode` skill's `install-git-hooks` action — invoke it to wire this into any other VS Code extension project.

**This project's version kept bumping on every commit, but NO git tag and NO GitHub Release was ever created for any of it — root-caused and fixed at the `smarts-git-automate`/`smarts-app-vscode` skill level, not here.** `smarts-git-automate`'s own per-commit tagging workflow assumed IT alone performed the version bump before tagging; because this project's own `githooks/pre-commit` hook already bumps `package.json` transparently inside `git commit` itself, the skill's tagging steps never actually ran (no agent turn ever executed them, since the bump appeared to already be "done"). Fixed generally in `smarts-git-automate` (detects a repo with its own self-bumping git hooks via `core.hooksPath`, skips re-deriving the version, and tags the commit's ACTUAL version instead — see that skill's own `module/workflow.md`) and in `smarts-app-vscode` (new `create-release` action: publishes a real GitHub Release from an already-pushed tag, attaching the matching `build/*.vsix`, verified via `gh release view` read-back). First real proof on this project: commit `8c8eb31` (v2.0.35) → tag `v2.0.35` → [Release v2.0.35](https://github.com/asror-z/smarts-claude-manager/releases/tag/v2.0.35) with the `.vsix` attached, all three confirmed via read-back rather than trusted from command exit codes. Going forward, after any commit lands (auto-bumping the version via the hooks), tag it and publish its Release as a separate, explicit follow-up step — never assume the commit alone produced either.

**The packaged `.vsix` was observed shipping stray session-scratch files** (`_launch_sample.cmd`, `_launch_sample_diag1.cmd`/`diag2`/`diag3`, `_verify_png.mjs`) because `.vscodeignore` had no catch-all exclusion for root-level scratch scripts left over from earlier debugging sessions — only `.md` files got a blanket exclude-then-reallowlist treatment (see above). **Fixed:** `.vscodeignore` now also has a bare `_*` pattern, excluding any root-level file whose name starts with an underscore (matching this project's own `_*`-prefixed scratch-file naming convention) — so a future package no longer silently ships debugging leftovers to end users.
