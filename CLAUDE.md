# Smarts Claude Manager — Project Requirements

VS Code extension (`zeyutang.smarts-claude-manager`) that patches the **Claude Code extension's own
bundled files** (`extension.js`, `webview/index.js`, `webview/index.css`) on disk to add UI knobs (font
sizes, diff-card options, plan-preview sizing) and a pack of always-on chat-webview behavior features
(search, export, date/time stamps, copy buttons, auto-continue on stream drop, etc.) that don't exist
natively in Claude Code.

## Build / Package / Test Commands

```bash
npm run compile          # tsc -p ./  (src/*.ts -> out/*.js)
npm run watch            # tsc -watch -p ./
```

There is no lint script and no test runner configured in `package.json`, and no `tests/` folder in this
repo. Verification is:
- Compile (`npm run compile`) and check for TypeScript errors.
- Run via **F5** (`.vscode/launch.json` "Run Extension" — opens an Extension Development Host window
  with this extension loaded; this project's default dev workflow).
- Ad-hoc scratch test scripts against a **disposable copy** of a real installed
  `anthropic.claude-code-*-win32-x64` extension folder (never the user's live `~/.vscode/extensions/`
  install) — the disk-mutating-apply/restore test pattern owned by `smarts-app-vscode` →
  `module/host-lifecycle.md`.
- Packaging: `vsce package` — see [Every `.vsix` Build Goes Into `build/`](#every-vsix-build-goes-into-build--owned-by-smarts-app-vscode) below.

## Architecture

### The patch target vs. this extension's own code

This extension's own code (`src/*.ts` → `out/*.js`, loaded as `main` by VS Code) is **not** what gets
patched. What gets patched is a **different, already-installed extension**: Anthropic's Claude Code
(`anthropic.claude-code-<version>-<platform>`), found by scanning the VS Code-family host's real
extensions directory for the newest matching folder (see `extensionsDirs()` below). Three files inside
that folder are the actual patch targets:

| File | What it controls |
|---|---|
| `extension.js` | Plan Mode preview webview (font sizes, CSP) |
| `webview/index.css` | Chat code-block font size, chat message-input-box (composer) font size, and related CSS |
| `webview/index.js` | Chat Edit/MultiEdit diff cards (a Monaco diff editor with hardcoded options), plus the injected chat-enhancement `<script>`/`<style>` block |

### `patcher.ts` — the patch engine (~2,600 lines, the core of this extension)

Everything about *how* a byte-level edit is made to Claude Code's files lives here. Three kinds of edits,
each with its own declarative table and apply/restore/analyze functions:

- **`PATCH_POINTS`** (`PatchPoint[]`) — a *size* swap: replaces a hardcoded px number or CSS value via an
  anchor regex. `pointSet()` / `pointRestore()` / `pointCurrentPx()`.
- **`TOGGLE_POINTS`** (`TogglePoint[]`) — a *boolean* flip (e.g. diff-card line numbers, the CSP patch,
  the always-on chat-enhancements injection gate). `toggleSet()` / `toggleCurrentOn()`.
- **`INJECT_POINTS`** (`InjectPoint[]`) — adds CSS/JS that doesn't exist natively (custom font family,
  the whole chat-enhancement feature bundle). `readInject()` / `injectEq()`.

Each point declares a `section: Section` (`"Chat Panel" | "Plan Preview"`) used to group rows in the
settings panel. `ALWAYS_ON_TOGGLES` (`chatEnhancements`, `faroCsp`) are toggles the UI can never turn off.

Top-level flow, in the order a caller actually invokes it:

1. **`findLatestClaudeExt(context)`** — resolves the real Claude Code install folder via
   `extensionsDirs(context)`, which reads `context.extensionUri` first (this is what makes discovery
   host-agnostic across every VS Code-family fork — see the "Must Work in EVERY VS Code-Based IDE"
   section below).
2. **`analyze()` / `analyzeToggles()` / `analyzeInjects()`** — read the three target files off disk and
   report each point's live status (`current` / `stock` / `custom` / `missing`) against the user's
   `smartsClaudeManager.*` settings — this drives the panel's green/yellow sync dots. Always a live read,
   never a cached assumption.
3. **`applyPatch()`** — the actual write. Loops over the three files; each file's edits are wrapped in
   their own try/catch (one file's write failure never aborts the others — see the EPERM/partial-apply
   incident further down), and every write goes through **`writeFileAtomic()`** (temp file + rename, with
   retry on `EPERM`/`EBUSY`/`EACCES` for Windows' transient post-update file locks).
4. **`restorePatch()`** — reverts every patched file back to its captured native/stock values
   (`captureStockValues()` records the pristine bytes the first time a file is touched, keyed by Claude
   Code version).
5. **`class Patcher`** (constructor + `register()`) — the stateful orchestrator: activation-time
   drift-check + `applyOnActivation()` (auto-applies and, if real edits were written, auto-reloads the
   window once), `discard()` / `enable()` / `restore()` for the panel's buttons, all gated on
   `smartsClaudeManager.patchEnabled`. `readSizes()` / `readToggles()` build the desired state from VS
   Code configuration; `readFeatureDefaults()` supplies per-feature on/off defaults.

### Chat-enhancement features — a separate injection layer

`behaviorFeatures.<id>.ts` (17 files — `faro`, `reply`, `googlesearch`, `search`, `datetime`,
`askquestion`, `userstyle`, `blockquote`, `copybuttons`, `codeblock`, `toc-export-scroll`, `askcollapse`,
`autocontinue`, `draftsave`, `usernav`, plus `behaviorToolbar.ts`/`behaviorBootstrap.ts` for shared
infrastructure) are
fundamentally different from a `PatchPoint`/`TogglePoint`/`InjectPoint`: those swap an *existing* value
already in the bundle, these add *new* client-side JS/CSS behavior that doesn't exist in the stock bundle
at all.

- **`behaviorFeatures.ts`** is the registry — each `behaviorFeatures.*.ts` module calls
  `registerFeature({id, label, js, css})` at import time; `patcher.ts` imports this registry and folds
  every feature's `js`/`css` into one `chatEnhancements` `TogglePoint`.
- **`behaviorInject.ts`** assembles the final injected block: one marker-tagged inline `<script nonce>` +
  one `<style>` block, spliced into `webview/index.js`/`index.css` right before `</body>`/the CSS end —
  never separate asset files with `<script src>` (the webview's CSP is `script-src 'nonce-${u}'` only).
  `escapeForTemplateLiteral()` doubles backslashes so injected text survives being re-embedded inside
  Claude Code's own outer template-literal source.
- **`behaviorBootstrap.ts`** is the shared runtime every feature's IIFE registers against
  (`window.__ccOnChatDoc`) — `document` already *is* the chat document in this VS Code webview target (no
  nested iframe to hunt for).
- Per-feature on/off is controlled **only** by its own `smartsClaudeManager.feature.<id>` VS Code
  setting, surfaced as a checkbox in the settings panel — there is no in-chat toggle UI and no master
  switch for the whole pack (it is always injected).

Full behavioral detail (Faro/CSP, DraftSave's storage-key history, AutoContinue's false-fire guards, and
more) is documented feature-by-feature further down in this file, under
["Chat-Enhancement Features Architecture"](#chat-enhancement-features-architecture) — consult it before
touching a `behaviorFeatures.*.ts` file.

### `panel.ts` — two webview hosts, one shared renderer

`abstract class PatchWebviewHost` owns `html()` / `knobHtml()` / `featureHtml()` / `onMessage()` /
`update()` — the actual UI rendering and message-handling logic. Two concrete subclasses reuse it against
VS Code's two different webview surfaces (`vscode.WebviewPanel` and `vscode.WebviewView` expose the same
`.html` / `.postMessage` / `.onDidReceiveMessage` / `.cspSource` interface):

- **`PatchPanel`** — a floating editor-tab panel, opened via the `smartsClaudeManager.panel` command.
- **`PatchSidebarView`** — an Activity Bar-docked sidebar view (`registerWebviewViewProvider`), lazily
  resolved the first time its Activity Bar icon is opened.

When adding a new panel feature, add it to the shared base class — adding it to only one subclass makes
the sidebar and the floating panel silently diverge. Full layout/CSS detail is under
["Two Host Surfaces, One Shared Control-Surface Renderer"](#two-host-surfaces-one-shared-control-surface-renderer)
further down.

### `extension.ts` — activation/deactivation

`activate()` runs two one-time settings migrations (`migrateNamespaceRename()` for the pre-2.0.0
`claudeCodeUiPatch` → `smartsClaudeManager` rename, `migrateLegacyKeys()` for pre-rename `chatDiff*` →
`chatDiffCard*` keys), then constructs `Patcher`, `StatusBar`, and `PatchSidebarView` and registers the
`smartsClaudeManager.panel` command. `deactivate()` is a deliberate no-op — see
["`deactivate()` Is a Pure No-Op"](#deactivate-is-a-pure-no-op--it-never-reverts-the-on-disk-patch)
below for why.

### `statusBar.ts`

A single status-bar item (`aA`) showing a hover summary of patch state; click opens the panel.

### Configuration surface

Every setting lives under the `smartsClaudeManager.*` namespace in `package.json`'s
`contributes.configuration.properties`. When adding a new config key, it must be declared in
`package.json` **and** wired into the matching `PATCH_POINTS`/`TOGGLE_POINTS`/`INJECT_POINTS` table in
`patcher.ts` (with a shipped default matching the JSON schema default) for the panel's drift-detection to
work correctly — see also
["Shipped Default vs Native Restore Value"](#shipped-default-vs-native-restore-value--owned-by-smarts-app-vscode)
further down.

## This Extension Must Work in EVERY VS Code-Based IDE, Not Just Plain VS Code — `extensionsDirs()` Is the Universal Discovery Mechanism

**`patcher.ts`'s `extensionsDirs(context)` resolves the running host's real extensions folder via `context.extensionUri` FIRST — this is the one mechanism that already works correctly no matter which VS Code-family fork is running this extension (VS Code, VS Code Insiders, VSCodium, Cursor, Windsurf, Trae, Antigravity IDE, …), with zero hardcoding.** A hardcoded fallback list (`.vscode`, `.vscode-insiders`, `.vscode-oss`, `.antigravity-ide`, `.antigravity`, `.cursor`, `.windsurf`, `.trae`, `.vscodium`) exists only for a DEFENSIVE secondary scan (e.g. Claude Code installed under a different IDE-family profile than the one this extension itself runs under) — each entry is only used if its `extensions/` folder actually exists on disk. Never assume that list is exhaustive; add a genuinely new fork's folder name there when discovered.

**Real incident — an extended, costly misdiagnosis from checking the wrong IDE's paths entirely.** A "patch not applying"/"chala apply" investigation repeatedly checked plain VS Code's `%APPDATA%\Code\User\settings.json` and `~\.vscode\extensions\`, concluding `patchEnabled: false` was the cause — while the user was running **Antigravity IDE** the whole time, a separate, unrelated VS Code fork with its own `%APPDATA%\Antigravity IDE\User\settings.json` and `~\.antigravity-ide\extensions\`. Once the correct paths were checked, `patchEnabled: true` matched reality and the extension was already fully and correctly applied. **The lesson: when diagnosing ANY "settings say X but the running app does Y" report, first confirm WHICH VS Code-family IDE the user is actually running** (ask, or read the real running workbench's own window title / a screenshot's own UI chrome — a VS Code-style Settings UI with a tab literally labeled "Antigravity IDE Settings" is a direct, unambiguous tell) before checking any settings/extensions path — never assume plain VS Code by default just because the codebase's own doc comments and most tooling default to `.vscode`-shaped paths.

## A Genuinely OLDER Extension Version Can Stay Permanently Active — Check `extensions.json`'s `pinned` Field, Never Assume the Newest `.vsix` Wins

**Real incident, this project, 2026-07-14/15:** after installing `smarts-claude-manager` v2.0.61, the panel kept showing **v2.0.24** — a version from many commits earlier, missing the `patchEnabled` gate, the EPERM-retry fix, the Faro/CSP patch, and the whole top-of-panel Enable/Disable toggle. Six version folders coexisted on disk (`...2.0.19` through `...2.0.61`); every one of v2.0.30 through v2.0.61 was correctly marked in `.obsolete`, yet the extension host kept activating v2.0.24 regardless of "Reload Window," a genuinely fresh chat panel/tab, or even a full app quit-and-relaunch. Root cause, found by reading Antigravity IDE's own `<extensions-root>/extensions.json` (the authoritative install registry): the `zeyutang.smarts-claude-manager` entry had **`"metadata": {"pinned": true, ...}`** pointing at the `...-2.0.24` folder — a VS Code-family install-state fact **entirely outside this project's own source code** (grep confirms nothing in `src/*.ts` ever reads or writes `pinned`/`installedTimestamp`/`extensions.json`). No amount of reinstalling a newer `.vsix` overrides a pinned entry; VS Code keeps reactivating the pinned version until it is explicitly unpinned or uninstalled through the Extensions UI.

- **The diagnostic tell:** the visibly-running panel shows an old feature set (missing checkboxes, old section headings like "Chat Enhancement Features" instead of "Chat Features") that doesn't match the newest committed UI — that mismatch, cross-checked against the version pill, is the signal to stop assuming "the newest install must be active" and go read `extensions.json` directly.
- **The fix is user-side, not code-side:** uninstall the stuck version via the Extensions view (gear icon → Uninstall) — never hand-edit `extensions.json`'s `pinned`/`installedTimestamp` fields directly, since that file is VS Code's own live state and an external edit risks corrupting the registry the running host has already loaded into memory — then fully restart the IDE and reinstall the intended `.vsix` via **Install from VSIX...**.
- **When a stuck old version is suspected, `git diff <old-version-tag/commit>..HEAD` is the right tool to rule OUT a code regression before chasing an install-state bug** — diffing this project's v2.0.24 commit (`4df7db8`, the parent of `9498822` which bumped to 2.0.25) against `HEAD` showed only deliberate feature additions (the `patchEnabled` gate, `deactivate()`'s file-revert, the CSP/Faro patch, the top-toggle UI) — nothing that would explain a newer version failing to activate, which is exactly the evidence that pointed at VS Code's own install-state instead of a source regression. The general form of this diagnostic — comparing an old-but-working version's tag/commit against the latest working-tree code file-by-file to isolate a regression, with the fallback of temporarily restoring specific old-version code into the working tree to unblock the user — is owned by `smarts-app-all` → `module/version-regression-diagnosis.md`; this project-local note only records the concrete incident and its resolution here.
- **This `pinned: true` behavior is a general VS Code-family fact, not Antigravity-IDE-specific — it recurred identically in plain VS Code** (2026-07-15): `zeyutang.smarts-claude-manager` showed `"pinned": true` in `~/.vscode/extensions/extensions.json` pointing at v2.0.63 (that time, correctly the newest version, so pinning itself wasn't the bug — but it confirms every VS Code-family host can pin an extension entry independent of which version is newest on disk). Always check `extensions.json`'s `pinned` field on ANY VS Code-family host when a version mismatch is suspected, not just Antigravity IDE.

## `deactivate()` Is a Pure No-Op — It NEVER Reverts the On-Disk Patch

**`extension.ts`'s `deactivate()` does nothing beyond letting VS Code clean up registered disposables — it deliberately never calls `Patcher.restoreFilesOnly()` or anything else that touches the on-disk bundle.** This went through two iterations, and the current, correct one is a pure no-op:

1. **Originally**, `deactivate()` was a comment-only stub (matching v2.0.24) — the only revert path was the panel's own toggle/button.
2. **Then**, to fix a real reported bug ("patch extension remove qilinsa ham patch applied turibdi" — the patched UI stayed active even after uninstalling/disabling this extension without first clicking the panel's toggle), `deactivate()` was changed to unconditionally call `Patcher.restoreFilesOnly()` (a synchronous, side-effect-free method reverting `extension.js`/`index.css` to native) via a module-level `activePatcher` reference.
3. **This turned out to be a WORSE regression**, discovered by directly diffing this extension's own working v2.0.24 commit against a later, misbehaving HEAD (per the general technique now owned by `smarts-app-all` → `module/version-regression-diagnosis.md`): `deactivate()` fires **identically** for an ordinary window reload and for a genuine uninstall/disable — VS Code's own API gives no way to tell them apart (confirmed against `microsoft/vscode#110034`, still open). So the unconditional revert reverted the patch on **every single reload**, not just a real removal, and whatever activated next had to re-apply it from scratch — a screenshot or check taken in that narrow revert-then-reapply window looked exactly like "the patch keeps failing/chala apply," when the revert itself was the actual bug. **Reverted back to a pure no-op**, exactly matching v2.0.24's behavior, which was rock-solid specifically because it never touched the disk except on activation.

**The accepted tradeoff (same one v2.0.24 always had):** a user who uninstalls/disables this extension **without** first using the panel's own Enable/Disable toggle leaves the patched bytes on Claude Code's disk until either they reinstall and toggle it off themselves, or Claude Code's own next auto-update overwrites `extension.js`/`index.css` natively anyway (which happens routinely). This tradeoff is deliberate and was reconfirmed directly by the user — stability of the common case (the patch staying correctly applied across ordinary reloads) outweighs cleanly reverting the rare case (an uninstall with no prior toggle click).

**Testing `applyPatch()`/`restorePatch()` follows the generic disk-mutating-apply/restore test pattern owned by `smarts-app-vscode` → `module/host-lifecycle.md`** (establish a clean baseline via a pre-clean `restorePatch()` + a second-call idempotency check before diffing; a plain-Node test `require()`ing the compiled `out/patcher.js` outside the extension host uses a minimal `vscode` stub via `Module._resolveFilename` and must pass realistic config/toggles). Project-specific gotcha to remember here: `applyPatch(ext, sizes, toggles, capture)` needs a REALISTIC `toggles` map — passing `{}` leaves `chatEnhancements` falsy, and since `ALWAYS_ON_TOGGLES` is enforced only inside `readToggles()` (which needs a real `vscode.workspace.getConfiguration()`, absent in a plain-Node test), an empty toggles map makes `applyPatch` **remove** the behavior-script injection instead of installing it — the opposite of production. Pass `readToggles()`-shaped toggles (or set the always-on ids true) in tests.

**When DIAGNOSING whether a real, live installed bundle is "correctly patched," always read the user's REAL `settings.json` values for the toggle in question before calling anything a bug — a toggle showing `status: "custom"`/a stock on-disk value is not automatically a defect.** Real incident: `webview/index.js`'s diff-card theme sync (`ccup-theme`) and line-numbers anchors appeared "stock"/unpatched on the live Antigravity IDE install, and `analyzeToggles()` reported both as `status: "custom"` against a **hardcoded** `{diffThemeSync: true, diffLineNumbers: true}` test input — which looked like the exact "chala apply" partial-patch bug from before. It wasn't: the REAL `settings.json` had `smartsClaudeManager.chatDiffCardThemeSync: false` and `chatDiffCardLineNumbers: false` explicitly set by the user, so the native/stock on-disk value was **the correct, intended output**, not a failed write. The `analyzeToggles(ext, toggles)` function takes the desired `toggles` map as a plain argument — it has no way to know a test's hardcoded map doesn't match the real config, so a mismatch there manufactures a phantom "drift"/"custom" status that looks identical to a genuine partial-apply failure. Before concluding "toggle X failed to apply," always cross-check the ACTUAL `smartsClaudeManager.*` settings.json values for that host/IDE (not an assumed or hardcoded "should be on" value) and pass `readToggles()`-shaped real values into any diagnostic `analyzeToggles`/`applyPatch` call.

**`autoApply()` and the `Patcher` constructor's activation-time drift-check are both gated on `smartsClaudeManager.patchEnabled` — a disabled patch must never silently re-apply.** Root cause of a related reported bug ("patch apply bolmayapti" investigated 2026-07-11): neither `autoApply()` nor the constructor's drift-check (`this.states.some(drifted) || ...`) ever read `patchEnabled` before writing the bundle. In practice this meant a patch the user had explicitly disabled via "Fully Disable Patch" (or that got left disabled by an uninstall/reinstall cycle) could still be silently re-patched the next time the extension activated, as long as some `smartsClaudeManager.*` setting differed from stock — contradicting the disabled state entirely. Fixed by adding `const enabled = vscode.workspace.getConfiguration(CONFIG_NS).get<boolean>("patchEnabled", true)` at the top of both `autoApply()` (early-return when `false`) and the constructor (folded into the `if` that gates the initial `void this.autoApply()` call). **On a genuinely fresh install, activation-time auto-apply from a pre-populated `settings.json` already worked correctly** (verified via a real scratch-copy test in `.claude/Chat Patch Extend/Tests/patchenabled-gate/run.mjs`: constructing a fresh `Patcher` against a scratch bundle with a drifted `chatCodeblockFontSize` and `patchEnabled: true` does write the patch on construction) — the actual gap was specifically the missing `patchEnabled` gate, not the auto-apply mechanism itself.

**When `smartsClaudeManager.patchEnabled` is on, the patch AUTO-APPLIES on extension activation AND auto-reloads the window ONCE on first application — so a fresh install takes effect immediately, with NO manual Disable/Enable.** Reported bug: after installing the extension the patch didn't work until the user manually toggled Disable→Enable. Root cause (per the generic "a disk change never live-updates an already-open webview" fact owned by `smarts-app-vscode` → `module/host-lifecycle.md`): the constructor's activation-time `autoApply()` correctly WROTE the patch to Claude Code's `extension.js`, but any already-open chat webview had loaded the pre-patch bundle — so it looked unpatched until Enable's own `reloadWindow` forced a reload. Fix: `applyOnActivation()` (called from the constructor in place of the bare `autoApply()` when the bundle is drifted and `patchEnabled` is on) applies the patch and, IF real edits were written (`autoApply()` now returns the changed-count), automatically reloads the window once. **No reload loop** — `applyPatch()` is idempotent (writes only on a real change), so after the reload the bundle is fully applied → the next activation's drift-check finds nothing drifted → `applyOnActivation()` is never called again; a `globalState` `activationReloadedFor` = `${extVersion}|${claudeVersion}|${changedCount}` stamp is a belt-and-suspenders stop against a stuck-anchor edge case degrading to the panel's reload button rather than a loop. Verified in `.claude/Chat Patch Extend/Tests/fresh-activate/reload.mjs` (activation 1 against a native bundle applies + reloads once; activation 2 against the applied bundle neither re-applies nor reloads).

**Enable/disable the whole patch via the TOP-OF-PANEL enable/disable toggle switch (`.patch-enabled-row`, `data-cmd="patchToggle"`), NOT a footer button — the old footer "Fully Disable Patch"/"Enable Patch" button was removed and replaced by this top switch per explicit user request.** The switch sits above the main `.card` (right under the `header-status`), styled as a prominent card-like row with the On/Off switch BEFORE the label (like a settings toggle), reusing the existing `.knob`/`.switch` styling. **Its label is DYNAMIC — it shows what a click will DO: "Disable patch" when the patch is currently on, "Enable patch" when off** (the `.patch-enabled-label` span; `snap.patchEnabled` is in `shapeOf()` so a state change full-re-renders it correctly). It reflects `snap.patchEnabled`; clicking it posts `command: "patchToggle"` with the CURRENT on-state (`msg.on`) — the handler interprets `on===true` as "user is turning it OFF → `patcher.restore()` (fully disable)" and `on===false` as "turning it ON → `patcher.enable()`". **It fires with NO confirmation dialog** (the earlier native Yes/No `confirmAction()` modal was removed per explicit user request — "modal confirm kerak emas! Automatically apply qilsin yoki remove qilsin!") — it applies/reverts immediately and automatically reloads the window right after (`workbench.action.reloadWindow`) so the effect is visible without a second click. It does NOT flip optimistically (the reload refreshes the real state either way). The remaining footer "Restore Last Applied" (`data-cmd="discard"`) still shows the native Yes/No modal via `confirmAction()` — only `patchToggle` had its confirm removed. Because `snap.patchEnabled` is part of `shapeOf()`'s structural string, a `patchEnabled` change triggers a full HTML re-render, so the top switch's On/Off always rebuilds correctly. The `restore`/`enable` message cases in `onMessage()` were removed as dead code — `patchToggle` calls `patcher.restore()`/`patcher.enable()` directly.

**"Chala apply bo'lmoqda" (partial patch application) was a REAL bug — Windows transiently locks a just-updated Claude Code extension's files, and a single file's write failure used to abort the WHOLE patch batch, silently leaving later files completely unpatched.** Root-caused from a real error toast: `EPERM: operation not permitted, rename '...extension.js.<pid>.<n>.tmp' -> '...extension.js'`, firing right after Claude Code auto-updated to a fresh version (a newly-extracted extension's files are briefly held open by Windows Defender/an indexer/the extension host's own read — almost always transient, gone within milliseconds). Two compounding defects: (1) `writeFileAtomic()` had zero retry — the very first `EPERM` threw immediately; (2) `applyPatch()`/`restorePatch()`'s single `for` loop over `extension.js` → `webview/index.css` → `webview/index.js` had no per-file error isolation, so `extension.js` (patched first, holding the chat-enhancements script + `faroCsp`) failing aborted the loop before `webview/index.css` (the behavior-CSS block — "interface looked dim, CSS wasn't loading") or `webview/index.js` (the diff-card toggles — "some features work, some don't") were ever reached, even though their content changes had already been computed and were ready to write. Fixed: `writeFileAtomic` now retries `EPERM`/`EBUSY`/`EACCES` on the rename step up to 5 times with a 50/100/150/200ms backoff before giving up; separately, each file's write in `applyPatch`/`restorePatch` is wrapped in its own try/catch, so one file's persistent failure is recorded in the returned `PatchReport.failed` (`{file, error}[]`) and reported to the user by name via `autoApply()`, while every OTHER file still gets its own write attempt regardless. Verified via a real scratch-copy test simulating both a transient lock (recovers automatically after 2 failed retries) and a persistent one (the locked file is correctly reported as failed while every other file still gets patched on disk) — `.claude/Chat Patch Extend/Tests/partial-apply-fix/run.mjs`, 6/6 assertions.

**The F5-vs-installed-copy load paths, the "running panel with no `~/.vscode/extensions/` folder is F5 not a broken install" diagnosis, the `.obsolete`/half-uninstalled install-state class, and "a disk change never live-updates an already-open webview" are all owned by `smarts-app-vscode` → `module/host-lifecycle.md` — consult it, do not re-derive them here.** Project-specific facts only: **this project's default dev workflow is F5 (developer mode)**, so a running "SMARTS CLAUDE MANAGER" panel with no `.vscode\extensions\zeyutang.smarts-claude-manager-*` folder is normal/expected. ## Chat-Enhancement Features Architecture

The 17 chat-webview behavior features (Faro, Reply, Google Search, Search, DateTime, AskQuestion, UserStyle, Blockquote, CopyButtons, CodeBlock, Toc, Export, Scroll, AskCollapse, AutoContinue, DraftSave, UserNav — one `behaviorFeatures.<id>.ts` file each, registered into `behaviorFeatures.ts`'s registry) are fundamentally different from every `PATCH_POINT`/`TOGGLE_POINT`/`INJECT_POINT` in `patcher.ts`: those swap an *existing* hardcoded value already in the bundle, whereas a chat-enhancement feature adds *new* client-side behavior that doesn't exist in the stock bundle at all.

**`googlesearch` (`behaviorFeatures.googlesearch.ts`) adds a custom item to the browser's own native `contextmenu` (right-click) on a text selection inside a chat message — the first feature in this project to hook `contextmenu` rather than render a floating button.** It reuses `reply.ts`'s exact selection-scoping helpers (`isInsidePromptInput`/`selectionIsInChat`) so the menu item never appears for text selected inside the composer (that's editing, not researching) — only for a selection inside a rendered chat message. On `contextmenu`, if the selection qualifies, it calls `e.preventDefault()` and renders its own small fixed-position menu (styled with `--vscode-menu-*` variables to match native VS Code context menus) positioned at the click coordinates, clamped to the viewport. Toggleable via `smartsClaudeManager.feature.googlesearch` (default on), like every other feature.

**The chat webview's iframe is sandboxed WITHOUT `allow-popups` — NEITHER `window.open()` NOR a real `<a target="_blank">` click can open a new browser window from injected webview JS.** Confirmed live via the actual DevTools console error: `"Blocked opening 'https://www.google.com/search?q=...' in a new window because the request was made in a sandboxed frame whose 'allow-popups' permission is not set."` Two things were tried and both failed identically, because the restriction blocks the *navigation itself*, not the API used to request it: (1) `window.open(url, "_blank", "noopener,noreferrer")` — silently blocked; (2) building a real `document.createElement("a")` with `target="_blank"` and calling `.click()` on it — blocked with the exact same console error. Claude Code's own `extension.js` never does this from webview content either — every one of its external-link opens goes through the extension host's `vscode.env.openExternal(vscode.Uri.parse(url))`, reached via a `postMessage` → the webview panel's `onDidReceiveMessage` → Claude Code's own private `s?.fromClient(a)`/`c?.fromClient(u)` message router (inside `setupPanel()`, the real chat-panel wiring function — viewType `"claudeVSCodePanel"`).

**`openExternalBridge.ts` (`patcher.ts`'s `openExternalHost`/`openExternalWebview` `TogglePoint`s, both `ALWAYS_ON_TOGGLES`) makes a REAL bridge to `vscode.env.openExternal` possible WITHOUT touching Claude Code's own dispatcher — two small, ADDITIVE patches, applied together:** (1) **`webview/index.js`**: the chat webview's own single, real `acquireVsCodeApi()` call (Claude Code's React chat app calls it exactly once — a second call there is a documented full-webview crash, see DraftSave's storage-key saga above) is wrapped, via the comma operator, into `(window.__ccVsCodeApi=acquireVsCodeApi())` — the SAME single call, used identically by Claude Code's own code, just also stashed on `window` so our injected script can read it without ever calling `acquireVsCodeApi()` itself. (2) **`extension.js`**: `setupPanel()`'s existing `e.webview.onDidReceiveMessage((u)=>{...c?.fromClient(u)},null,this.disposables)` registration is followed by a **second, independent** `onDidReceiveMessage` call on the *same* `e.webview` — `vscode.Webview.onDidReceiveMessage` is a plain multi-listener event, so this coexists safely; ours only recognizes `{type:"ccOpenExternal",url}` and calls `<alias>.env.openExternal(<alias>.Uri.parse(u.url))` (the `vscode` module alias — e.g. `Tt` — is captured LIVE from the nearby `<alias>.window.createWebviewPanel("claudeVSCodePanel",...)` call in the same closure, never hardcoded), leaving Claude Code's own `c?.fromClient(u)` dispatch completely untouched. `behaviorFeatures.googlesearch.ts`'s `openGoogleSearch()` tries `window.__ccVsCodeApi.postMessage({type:"ccOpenExternal",url})` first and only falls back to copying the URL to the clipboard (`navigator.clipboard.writeText`, with the `execCommand("copy")`-via-hidden-`<textarea>` legacy fallback `copybuttons.ts` already established, plus a `#cc-googlesearch-toast` confirmation) if the bridge object is absent — e.g. a future Claude Code build renames/restructures either anchor, in which case both `TogglePoint`s' `fnPresent` (anchor-or-marker, mirroring `chatEnhancementsPresent`'s own semantics) simply return false and the loop skips them, never throwing or corrupting either file. Verified end-to-end against a scratch copy of the real installed `anthropic.claude-code-2.1.214` bundle (`.claude/googlesearch-diag/Tests/test-bridge.mjs`, 24/24 assertions): both markers apply correctly, `acquireVsCodeApi()` still occurs exactly once after patching, the captured `Tt` alias and `Uri.parse(u.url)` call are correct, Claude Code's own `c?.fromClient(u)` dispatch is untouched, both files stay valid JS, re-applying is a no-op (idempotent), and `restorePatch()` reverts both files byte-for-byte including the exact original `acquireVsCodeApi()` call site. **Any FUTURE feature that needs to open an external URL from the chat webview reuses this same bridge** (`window.__ccVsCodeApi.postMessage({type:"ccOpenExternal",url})`) rather than re-deriving a new one.

**Faro (`behaviorFeatures.faro.ts`) is the shared logging sink every OTHER feature calls through — imported FIRST in `patcher.ts` so `window.__ccFaroLog` exists before any later feature's `init()` might use it.** It ships structured diagnostics to Grafana Cloud (console + Loki, via the Faro Web SDK loaded from the unpkg CDN — the Loki push endpoint itself doesn't answer a browser's CORS preflight, so Faro's collector is the CORS-safe path) and monkey-patches `console.*` so raw console calls are mirrored too. **Reaching Loki requires the `faroCsp` CSP patch AND the nonce'd `loadScript` (both documented below); with the stock CSP, Faro is console-only because the SDK load and collector POST are both blocked.** Deployed via `smarts-logging-grafana action=apply arch=skill path=<this-project>` — its stamped `FARO_COLLECTOR_URL`/`FARO_APP_NAME` constants are a public write-only ingest identifier (not a secret; safe to commit), re-run that skill rather than hand-editing them if the collector ever changes. **Gating is per-feature, not a single master switch:** `window.__ccFaroLog(channel, fields, level, callerModule)` checks BOTH Faro's own `smartsClaudeManager.feature.faro` checkbox AND the calling feature's own checkbox (`window.__ccFeature(callerModule)`) — a feature that is itself toggled OFF never logs, even while Faro/Logging stays ON ("qaysi feature yoqilgan bo'lsa - o'sha feature log yozadi, o'chirilgan bo'lsa yozmaydi"). A caller with no module id (the wrapped bare `console.*`) is gated by Faro's own switch alone.

**Faro CANNOT reach Grafana Loki from Claude Code's chat webview unless the patch also rewrites that webview's CSP — the `faroCsp` always-on `TogglePoint` (in `patcher.ts`, added to `ALWAYS_ON_TOGGLES` alongside `chatEnhancements`) does exactly that.** Claude Code's chat webview CSP is `default-src 'none'; ${p}; ${f}; ${m}; script-src 'nonce-${u}'; ${v};` (style/font/img/worker via `cspSource`, script nonce-only) with **no `connect-src` and no host allowlist for scripts** — so both the unpkg Faro SDK `<script>` load AND the collector POST are blocked, and Loki gets zero data (confirmed live: "Loading the script 'https://unpkg.com/@grafana/faro-web-sdk…' violates … script-src 'nonce-…'. The action has been blocked", and `query_loki_stats` returning 0 streams). Faro worked in the sibling `smarts-claude-patch` project only because an **older Claude Code build's CSP permitted it** — Claude Code has since tightened it, so this is a real regression to restore, not a new feature. The fix mirrors that reference project's proven CSP edit (`d:\Machine\Coding\App\code.claude.com\VSCode\ALL\Claude Code for VS Code\Manager\smarts-claude-patch\smarts-claude-patch\scripts\Apply Patch.mjs` step 3d — **kept as the study reference for the working Faro/CSP approach**): (1) insert `connect-src <faro collector origin>;` right after `default-src 'none';` (or replace an existing `connect-src`), and (2) add `https://unpkg.com` to the existing `script-src 'nonce-${u}';` (nonce var captured fresh via `/script-src\s+'nonce-\$\{(\w+)\}'\s*;/`, **never hardcoded** — survives a re-minify that renames it). **The transform matches the WHOLE chat CSP `<meta>` (anchored on the template-literal `nonce-${u}` form via `CSP_CHAT_META_RE`) and edits only that matched substring** — a naive `split("default-src 'none';")` hits BOTH the chat CSP and the SEPARATE plan-mode-preview CSP (which shares the `default-src 'none';` prefix but uses a **literal** `nonce-{{NONCE}}` and `img-src data:`), a real bug caught in testing; scoping to the template-literal-nonce meta is what leaves the plan-preview CSP byte-for-byte untouched. It is idempotent, and `restorePatch()` reverts it byte-for-byte (verified via `.claude/Chat Patch Extend/Tests/csp-patch/` — 20 unit assertions on the transform + 8 end-to-end assertions applying the compiled `applyPatch`/`restorePatch` to a scratch copy of the real installed `anthropic.claude-code-2.1.207` bundle, all green: ON adds both directives, plan-preview stays literal, exactly one `connect-src` is added, restore round-trips). Because it is ALWAYS ON (no user-facing setting), it rides with the always-on chat-enhancements pack rather than being independently toggleable — it exists solely to make that pack's own Faro logging able to reach Grafana.

**The chat-enhancement features are NEVER the thing that's broken when "patch ishlamayapti" is reported — the injected features load and run correctly; a Faro-side defect (the `window.onerror` flood) is what makes them LOOK dead.** Definitive real-console evidence: all 17 `[cc-*] … loaded` lines fire and `[cc-datetime] sweep candidateCount=N docHasChat=true` shows the bootstrap finds the real chat DOM and features actively sweep it — the injection, nonce, and DOM-detection (`CHAT_PROBE` matching `userMessage_<hash>`/`messageContainer_<hash>`) all work. The fix (in `behaviorFeatures.faro.ts`'s `init()`): the error handler now pushes captured errors **straight to Faro (never through `logRecord`/`console.*`, so it can't re-enter the wrapped console)**, **de-dupes** an identical message within 2s, and **hard-caps** total captures at 50 — so a runaway upstream crash can never flood again while a genuine one-off error is still recorded. When a future "the patch isn't working" report comes in, the FIRST diagnostic step is the real chat-panel DevTools console (right-click inside the chat/composer → Inspect Element, NOT `Help > Toggle Developer Tools`), and the `[cc-*] loaded` + `docHasChat=true` lines are the proof the features are actually live — never conclude "broken" from console noise alone.

**To check whether the injected `<script nonce="${u}">/*ccup-behavior*/…</script>` block is syntactically valid, simulate the OUTER template-literal evaluation Claude Code's own `getHtmlForWebview()` performs — never run `vm.Script`/`new Function` directly against the raw on-disk `extension.js` bytes.** Real incident: reading `extension.js` from disk and syntax-checking the text between the `ccup-behavior` marker and `</script>` reported `SyntaxError: Invalid regular expression flags` at the Faro feature's `url: (FARO_COLLECTOR_URL || "").replace(/\\/collect\\/.*/, …)` line — but this was a **false positive**: the on-disk file is Claude Code's own JS **source**, which is itself one giant template literal (`` `...${u}...` ``) that our injected block sits inside as literal text; `escapeForTemplateLiteral()` (in `behaviorInject.ts`) deliberately doubles every backslash in the injected text so it **survives** that outer template literal being re-parsed as JS source, and those doubled backslashes are only meant to collapse back to single ones when the OUTER template literal actually **evaluates** at runtime (inside the real extension host, producing the HTML a browser parses) — never when reading the static file. The correct verification is: extract the raw slice, wrap it in a real backtick template literal via `new Function('u', 'return \`' + slice.replace(/\`/g,'\\\\\`') + '\`;')(fakeNonce)`, THEN syntax-check the **evaluated** result. Confirmed via this correct method: the injected script (both in general and the currently-installed bundle) is syntactically valid — there was no real bug. When a future "zero `[cc-*]` console lines" report needs static verification, use the evaluated-template-literal method, not a raw-source check, or it will manufacture phantom syntax errors.

**A dynamically-created `<script src=…>` in the chat webview MUST carry the page's live nonce or CSP blocks it — `loadScript()` in `behaviorFeatures.faro.ts` reads the nonce from an existing nonced `<script>` and sets BOTH `s.nonce` and the `nonce` attribute.** The webview's `script-src 'nonce-<u>'` admits a dynamically-injected script only when it carries that exact nonce; a `pageNonce()` helper reads it from `document.currentScript.nonce` first, else the first `script[nonce]` element on the page (our own injected block or Claude Code's `index.js` module script — both carry the same live nonce). Setting both the `nonce` property AND the reflected attribute is required (Chromium clears the reflected attribute after parse, so the property is the reliable carrier). This is necessary but NOT sufficient on its own — the `connect-src` from the `faroCsp` patch above is still needed for the collector POST; the nonce only unblocks the SDK *script* load.

**DraftSave now uses a SINGLE GLOBAL localStorage key (`cc-draft:global`), not a per-chat key** — the third and final abandonment in the per-chat-key saga documented below. localStorage in this VS Code build is partitioned by webview TYPE/origin (confirmed via live testing across Reload Webview/Reload Window), not by webview instance, so it already survives every reload on its own; the real bug across every earlier attempt was always the volatile per-chat KEY, never the storage medium. Tradeoff accepted: the draft is not chat-specific, so switching chats can surface another chat's last draft — mitigated by (a) a `sessionStorage`-based "does this look like a reload of the same instance" best-effort guard, and (b) a 10-minute staleness TTL past which a saved draft is treated as expired and never restored. Every save/restore/clear/expire is logged via Faro (module id `draftsave`) — length/metadata only, never the draft text.

## Chat Composer Font Size — Two Stacked Elements Share One Hash; Patching Only One Is Invisible

The chat message-input box (composer) is actually **two stacked elements sharing one CSS-module hash**,
not a single `<textarea>`: the real `contenteditable` div (`role="textbox"`, `aria-label="Message input"`,
className `messageInput_<hash>`) is painted **invisible** (`color:#0000` in the stock CSS — it exists only
to hold the caret/selection and receive input events), while a sibling `aria-hidden` div, className
`mentionMirror_<hash>`, is positioned absolutely on top and is what **actually renders the visible text**
(including @-mention highlighting). **A patch that only sizes `messageInput_<hash>` changes the invisible
layer's metrics but leaves the visible text's size untouched** — confirmed live: the first cut of this
knob patched `messageInput_<hash>` alone, and the user reported exactly this symptom ("korinmaydigan
fontning size ozgarvotti, korinadigan esa ozgarmadi" — the invisible font's size changed, the visible one
didn't). Both classes share the same hash suffix as the third sibling rule `messageInputContainer_<hash>`,
so the fix sizes **both** together in one rule. Claude Code's own CSS sets no `font-size` on either, so
they silently inherit the webview's base font-size (~13px). Because there is no existing numeric value to
regex-swap, the `chatComposer` `PATCH_POINT` (`patcher.ts`, `webview/index.css`) follows the exact same
append pattern as `chatCode` (the code-block font point): it appends a marker-tagged
`/*cc-ui-patch:chatComposer*/.messageInput_<hash>,.mentionMirror_<hash>{font-size:<px>px !important}`
line, re-reading the hash at patch time from the stock `.messageInputContainer_<hash>{...}` rule so it
survives a re-minify that changes the hash. Exposed as `smartsClaudeManager.chatComposerFontSize` (default
14px; `originalPx: 13` is the true native/inherited stock, used only for the restore-to-stock path —
setting the knob to exactly 13 removes the marker line entirely rather than writing a redundant `13px
!important`). Verified end-to-end against a scratch copy of the real installed extension: apply
writes/updates the marker (both selectors) in place (no duplicates across repeated value changes), and
restore reverts `webview/index.css` byte-for-byte to baseline. **The lesson for any future
composer/contenteditable patch point in this project: always check for a sibling mirror/overlay class
sharing the same hash before assuming the element you found in the DOM inspector is the one that's
actually visible** — a `color:#0000`/`visibility:hidden` rule on the "obvious" target is the tell.

## Toggle Switches Show No "On"/"Off" Text — the Switch's Own State IS the Label

Every toggle switch in the panel (`panel.ts`) — both the regular knob rows (diff card line numbers, diff

(`<span class="switch-track"><span class="switch-thumb"></span></span>`), with NO `<span
class="switch-text">On/Off</span>` alongside it. This was removed per explicit user request: the text
label was stealing horizontal space from the row's own title, forcing long titles ("diff card line
numbers") to wrap onto a second line even though the switch's position (left/right) and color (green/gray)
already convey on/off state unambiguously. The now-dead `.switch-text` CSS rules were removed too; the
live-update JS (`setToggleBtn()`) no longer looks for a `.switch-text` element to update. The panel's
outer `body` padding was also tightened (`18px 24px 24px` → `14px 14px 18px`, and a narrower `10px 10px
14px` + `.card` `12px 10px` inside the `@media (max-width: 500px)` sidebar breakpoint) — the wide
left/right padding was wasting horizontal room specifically in the Activity Bar sidebar's narrow real
width (~250–350px), where every pixel matters.

## Two Host Surfaces, One Shared Control-Surface Renderer

The control panel (font-size knobs, toggles, the Chat Features grid) is hosted on TWO separate VS Code surfaces that share one rendering/message-handling implementation:

- **`PatchPanel`** — a floating editor-tab `WebviewPanel` (`vscode.window.createWebviewPanel`), opened via the `smartsClaudeManager.panel` command (Command Palette or status-bar click).
- **`PatchSidebarView`** — an Activity Bar-docked `WebviewView` (`vscode.window.registerWebviewViewProvider`, view id `smartsClaudeManager.sidebarView`, icon `media/activitybar-icon.svg`), resolved lazily the first time the user opens it from its own Activity Bar icon.

Both extend the abstract `PatchWebviewHost` base class in `panel.ts`, which owns `html()`/`knobHtml()`/`featureHtml()`/`onMessage()`/`update()` — `vscode.WebviewPanel.webview` and `vscode.WebviewView.webview` expose the identical `vscode.Webview` interface (`.html`, `.postMessage`, `.onDidReceiveMessage`, `.cspSource`), so one implementation drives both hosts; only creation/reveal/lazy-resolution differs per subclass. When adding a new panel feature (a new command, a new message type), add it to the shared base, not to one subclass only — otherwise the sidebar and the editor-tab panel silently diverge.

**The panel must work at TWO very different widths — the wide editor-tab panel AND the Activity Bar sidebar's real narrow width (~250-350px)** — a single fixed-width knob-row design (label + a 168px `▼`/▲`/px control group) cannot fit the sidebar at all, and a horizontal-scroll fallback was tried and rejected (it left the controls clipped to unusable slivers). The actual fix is a real `@media (max-width: 500px)` breakpoint in `baseCss`: `.feature-grid`/`.section-grid` collapse to a single column, and the bottom `.actions` row stacks its buttons full-width (one per row, taller with a smaller icon/font) instead of sitting side-by-side (a multi-up layout truncated a footer button's label down to unreadable slivers). Each `.knob` row stays on ONE line even here — the `▼`/`▲` spinner buttons were replaced with a plain `<input type="number">`, and in the narrow view the input/switch is moved BEFORE the label via CSS `order` (not DOM reordering), with the label truncating via `text-overflow: ellipsis` instead of wrapping to a second line. When changing the panel's layout CSS, always check BOTH the wide (`section-grid`'s 3-column shape) and narrow (`@media (max-width: 500px)`) rules — a change to one that isn't mirrored in the other will look fine in the editor tab and break in the sidebar, or vice versa. Two universal webview-CSS-authoring pitfalls hit while building this panel (a `@media` block must be the LAST rule in a stylesheet, and `baseCss`'s backtick-delimited template literal must never contain a raw backtick, even in a comment) are owned by the `smarts-app-vscode` skill's `module/webview-css-authoring.md` — invoke it for any future CSS-cascade or template-literal-authoring issue, in this project or any other.

**The footer `.actions` row holds up to THREE buttons, in this fixed order: Restore Last Applied → Open VS Code Settings → Reload window to apply changes (the last only rendered while a reload is pending).** The former "Fully Disable Patch"/"Enable Patch" footer button was REMOVED — its function now lives in the top-of-panel "Enable / Disable patch" toggle (see the patchToggle paragraph above); do not re-add it to the footer. "Restore Last Applied" (`.btn-green`, `data-cmd="discard"`) reverts uncommitted knob changes to the last-applied floor. The pending-reload action used to be a clickable banner in `.header-status` under the title; it was moved into the footer as its own button (`statusInner()` returns an empty string for the `needsReload` case, and `.header-status:empty` collapses its margin so no gap is left). Since `needsReload` is not part of `shapeOf()`'s structural-shape string (only `snap.supported`/`snap.version`/`snap.patchEnabled`/the knob-id list are), a reload-pending transition arrives as a lightweight `sync` postMessage rather than a full HTML re-render — the client-side `sync` handler therefore creates/removes the reload `<button>` element in place (`document.querySelector('.actions')`) rather than relying on the full-render HTML.

**DraftSave restores the saved composer draft on the very next available frame after the composer element exists, never after a fixed timer delay.** An earlier version called `restoreIfEmpty()` from a flat `setTimeout(..., 300)` in `init()`, which visibly rendered the composer small/empty first and then, 300ms later, abruptly grew it once a saved multi-line draft was inserted — a jarring "pop" on every tab open (reported live: "tab ni ochganda shunaqa bolib ochilvotti boshida, keyin kattalashib qolmoqda"). The fix polls for `findComposer()` at `requestAnimationFrame` cadence (falling back to a 16ms `setTimeout` loop, capped at 60 tries ≈ 1s) and calls `restoreIfEmpty()` on the very first frame the composer is found, instead of waiting on an arbitrary timer — this generalizes: any injected feature that needs to act on a chat element "shortly after mount" should poll for that element's actual existence, not sleep a guessed delay.

**The correct DevTools target for any `[cc-*]` console.log/console.error diagnostic is reached by right-clicking directly inside the chat panel/composer → Inspect Element**, which opens a separate devtools window scoped to that webview's iframe — NOT the main VS Code workbench console (`Help > Toggle Developer Tools`), which never shows `[cc-*]` feature logs. Confusing the two consoles cost real debugging time on this project; always confirm which console a `console.log`/`console.error` actually landed in before drawing conclusions from its absence.

**AskCollapse (`behaviorFeatures.askcollapse.ts`) works around a stale AskUserQuestion suggestion chip visually persisting across a VS Code editor TAB switch.** Reported live: a floating suggestion card ("yana qanday model/engine/platform") from one tab stayed visible, overlapping the composer/toolbar, of a DIFFERENT tab that became active — clearing only after switching away and back once more. Root cause is a VS Code webview suspend/resume rendering artifact, not a DOM node our script owns or creates: a hidden tab's webview is throttled, so a suggestion chip mid-animation/reposition at the moment the tab loses visibility can freeze mid-frame and repaint stuck once the frame resumes on whichever tab is active then. The fix is NOT to hunt for "the" stale element by identity (there is none — it is a frozen paint, not leaked state) but to force a browser reflow of any floating (`position:fixed`/`absolute`), question-scoped element the moment `document.visibilityState` becomes `"visible"` again (`resweepOnVisible()`, wired via a `visibilitychange` listener in `init()`) — toggling `display:none` then back and reading `offsetHeight` in between forces the engine to recompute layout/paint instead of reusing the frozen frame. This is a workaround for a rendering artifact, not a root-cause fix (the true cause lives in VS Code/Chromium's own webview compositor); if it stops being sufficient, the next escalation is a forced repaint of the whole document (a `transform` no-op toggle on `document.body`) rather than just the individual floating element.

**DraftSave's storage-key history (ROOT-CAUSE FIXED — three options tried, Option 3 is what shipped):**

1. **Option 0 (root cause, historical) — `chatId()` originally read a `session=` query param that DOES NOT EXIST anywhere in this target's real webview URLs.** Every webview URL actually observed in this VS Code Claude Code build is shaped `index.html?id=<uuid>&parentId=<n>&origin=<uuid>&swVersion=<n>&extensionId=Anthropic.claude-code&platform=electron&...` — there is no `session=` param at all, only `id=` (per-webview-**instance**, confirmed to differ across multiple simultaneously-open chat panels). Because `chatId()` only recognized `session=`, it always returned `null`, so `draftKey()` was always `null` and both `saveNow()`/`restoreIfEmpty()` permanently no-opped — **DraftSave never actually saved or restored anything**, despite looking fully implemented in isolation.
2. **Option 1 (switch `chatId()` to read `id=` instead of `session=`) landed, then was CONFIRMED INSUFFICIENT by real user testing** ("DraftSave UMUMAN ISHLAMADI! reload webview and reload windiws da ham ishlamadi umumn yoqolib qoldi" — completely stopped working; Reload Webview AND Reload Window both lost the draft). `id=` genuinely regenerates on both a webview-only reload and a full window reload in this real build — the trade-off documented at landing time (works within a live tab session, not across any reload) turned out to be too narrow, since a reload is a common real-world case.
3. **Option 2 (`vscode.setState()`/`getState()` via a SECOND `acquireVsCodeApi()` call) is CONFIRMED UNSAFE and PERMANENTLY ABANDONED — it crashed the entire chat webview.** The temporary probe (`probeVsCodeApi()`) was live-tested and the real result was the chat panel crashing with "Something went wrong / Re-launch the extension to continue / Error rendering content: Encountered errors while disposing of store" — `acquireVsCodeApi()` can only be called once per webview; Claude Code's own extension code already calls it for its React/Redux store's postMessage/setState plumbing, and the second call throws during the chat webview's bootstrap, corrupting that store's init. **`acquireVsCodeApi()` must NEVER be called from any injected chat-enhancement script, under any circumstance** — this is the confirmed root cause of a full chat-panel crash, not a theoretical risk.
4. **Option 3 (SHIPPED) — a single GLOBAL localStorage key (`cc-draft:global`), not per-chat at all.** The insight that unblocked this: localStorage in this VS Code build is partitioned by webview TYPE/origin, not by webview instance, so it already survives every reload on its own — every earlier option's real bug was the volatile per-chat KEY, never the storage medium. A fixed, non-per-chat key sidesteps the whole "how do we get a stable per-chat id" problem, at the accepted cost of the draft not being chat-specific (switching chats can surface another chat's last draft). Two mitigations: (a) a `sessionStorage`-based best-effort "does this look like a reload of the same instance" guard (`looksLikeReload()`/`markInstanceLive()` — `sessionStorage`, unlike `localStorage` in this build, is scoped to the browsing context's own lifetime); (b) a 10-minute staleness TTL (`STALE_MS`) past which a saved draft is treated as expired and never restored. Every save/restore/clear/expire routes through the Faro Logging feature (module id `draftsave`) — length/metadata only, never the draft text.

## Every `.vsix` Build Goes Into `build/` — Owned by `smarts-app-vscode`

**`.vscodeignore` excludes every root-level `.md` by default, re-including only `README.md`/`readme.md`/`CHANGELOG.md`/`changelog.md`, plus `build/**` and `*.vsix` explicitly.** A stray untracked `.md` at the project root (e.g. a skill-generated `"Skill Installer Roadmap 2.md"` left over from an unrelated session) was leaking into the packaged `.vsix`'s file listing — `.vscodeignore` had no catch-all for "any Markdown that isn't a known user-facing doc." Any future root-level doc added to this project (a new user-facing manual, etc.) must get its own `!<name>.md` re-include line in `.vscodeignore`, or it silently drops out of the shipped package.

## Every Commit Auto-Bumps the Version and Auto-Builds a `.vsix` — Owned by `smarts-app-vscode`

This project's `core.hooksPath` is set to its tracked `githooks/` folder (`git config core.hooksPath githooks`, a per-clone local setting a fresh clone must re-run once). `githooks/pre-commit` deterministically bumps `package.json`'s patch version and stages it into the same commit; `githooks/post-commit` then compiles and packages a fresh `.vsix` into `build/` for that version — no model/LLM involvement at commit time, and no manual version bump going forward. Both hooks are thin shims calling the shared canonical script `~/.agents/githooks/Auto Version Build.mjs`, reused by every VS Code extension project. The general convention (the shared-script design, the Windows `.cmd`-spawn + shell-quoting pitfalls already fixed in it, and how to wire this into a new project) is owned by the `smarts-app-vscode` skill's `install-git-hooks` action — invoke it to wire this into any other VS Code extension project.

**This project's version kept bumping on every commit, but NO git tag and NO GitHub Release was ever created for any of it — root-caused and fixed at the `smarts-git-automate`/`smarts-app-vscode` skill level, not here.** `smarts-git-automate`'s own per-commit tagging workflow assumed IT alone performed the version bump before tagging; because this project's own `githooks/pre-commit` hook already bumps `package.json` transparently inside `git commit` itself, the skill's tagging steps never actually ran (no agent turn ever executed them, since the bump appeared to already be "done"). Fixed generally in `smarts-git-automate` (detects a repo with its own self-bumping git hooks via `core.hooksPath`, skips re-deriving the version, and tags the commit's ACTUAL version instead — see that skill's own `module/workflow.md`) and in `smarts-app-vscode` (new `create-release` action: publishes a real GitHub Release from an already-pushed tag, attaching the matching `build/*.vsix`, verified via `gh release view` read-back). First real proof on this project: commit `8c8eb31` (v2.0.35) → tag `v2.0.35` → [Release v2.0.35](https://github.com/asror-z/smarts-claude-manager/releases/tag/v2.0.35) with the `.vsix` attached, all three confirmed via read-back rather than trusted from command exit codes. Going forward, after any commit lands (auto-bumping the version via the hooks), tag it and publish its Release as a separate, explicit follow-up step — never assume the commit alone produced either.

**The packaged `.vsix` has been observed shipping stray session-scratch files** (`_launch_sample.cmd`, `_launch_sample_diag1.cmd`/`diag2`/`diag3`, `_verify_png.mjs`) because `.vscodeignore` has no catch-all exclusion for root-level scratch scripts left over from earlier debugging sessions — only `.md` files get a blanket exclude-then-reallowlist treatment (see above). Any root-level `_*`-prefixed or otherwise clearly-scratch file needs its own explicit `.vscodeignore` exclusion line, or a general `_*` pattern, so a future package doesn't silently ship debugging leftovers to end users. Not yet fixed as of this writing — flagged here so it isn't lost.
